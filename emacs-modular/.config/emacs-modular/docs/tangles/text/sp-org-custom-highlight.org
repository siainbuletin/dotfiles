A tiny module that makes Org inline export snippets of the form =@@comment:...@@= stand out visually, so they can be used as review notes inside running text. It defines one face and adds a font-lock rule in =org-mode-hook=.
- the current solution only makes the comments more visible

The file is required by =sp-org-ext=, To use it, it would need a =(provide 'sp-org-custom-highlight)= line and a =require= from one of the Org modules.

** The comment face

Org’s export snippet syntax ~@@backend:text@@~ is inline, and if no backend is named comment, every exporter drops it. That makes ~@@comment:like this@@~ a native inline comment that never appears in exported output. Org doesn’t style it by default, so add a font-lock rule:

Defines =my-org-inline-comment=, which inherits =lazy-highlight=. That face is themed by =sp-themes= (see /Search highlight that follows the theme/ in [[file:../ui/sp-themes.org][its doc]]): the =sp-dark= and =sp-light= themes take it from their palette, any other theme gets a tint of its keyword colour over its background. So the comment box follows the theme and is no longer fixed pale yellow. The inheriting face updates by itself on a theme change, with no hook.

#+begin_src emacs-lisp -i
(defface my-org-inline-comment
  '((t :inherit lazy-highlight))
  "Face for @@comment:...@@ inline comments.
Inherits `lazy-highlight', which `sp-themes' tints from the theme in use.")
#+end_src

** Font-lock rule in Org buffers

On every Org buffer, adds a font-lock keyword that matches =@@comment:= followed by text up to the closing =@@=.

- The two delimiters are shown in the =shadow= face, so they fade into the background.
- The comment body gets =my-org-inline-comment=.
- The pattern stops at a newline or at =@@=, so a comment cannot span lines or contain =@@=; a single =@= (as in =[cite:@key]=) is fine.
- The rule is appended after Org's own keywords and uses =prepend=, so it layers on top of existing fontification.

#+begin_src emacs-lisp -i
(add-hook 'org-mode-hook
          (lambda ()
            (font-lock-add-keywords
             nil
             '(("\\(@@comment:\\)\\(\\(?:[^@\n]\\|@[^@\n]\\)*\\)\\(@@\\)"
                (1 'shadow prepend)
                (2 'my-org-inline-comment prepend)
                (3 'shadow prepend)))
             'append)))
#+end_src

** Insertion command so you don't always type it out

=sp-org-insert-inline-comment= (bound to =C-c h= in =org-mode-map=) has two modes.

- No active region: inserts =@@comment:@@= and leaves point between the colon and the closing =@@=, so you can type the note.
- Active region: wraps the selected text in =@@comment:= ... =@@=, instead of replacing it.

Rules for the region case:

- Each non-blank line of the region becomes its own comment.
  - Why: the font-lock rule above matches one line only, so a comment across lines would export fine but never be highlighted.
  - Indentation and trailing spaces stay outside the comment markers.
  - Blank lines stay blank, so paragraph breaks are kept (an inline object cannot cross a blank line in Org anyway).
- Point at the start or at the end of the region gives the same result.
- A region holding =@@= is refused with a =user-error=, because the text would end the snippet early. Nothing is changed.
- A region with only whitespace counts as no region (the empty comment is inserted at point).
- The region is replaced in one edit, so one =undo= restores the text.
- The mark is deactivated and point ends after the last comment, so pressing =C-c h= again does not wrap the comment a second time.
  - Before, the mark stayed active over the new comment, so the second press nested another =@@comment:= inside the first.

#+begin_src emacs-lisp -i
(defun sp-org--comment-lines (text)
  "Return TEXT with each non-blank line wrapped as an inline comment.
Leading and trailing whitespace of a line stays outside the markers."
  (mapconcat
   (lambda (line)
     (if (string-blank-p line)
         line
       (string-match "\\`\\([ \t]*\\)\\(.*?\\)\\([ \t]*\\)\\'" line)
       (concat (match-string 1 line)
               "@@comment:" (match-string 2 line) "@@"
               (match-string 3 line))))
   (split-string text "\n")
   "\n"))

(defun sp-org-insert-inline-comment ()
  "Wrap the active region in `@@comment:...@@', or insert an empty one.
With a region, each non-blank line becomes its own comment, so the
highlighting (one line only) matches the export.  Without a region,
insert `@@comment:@@' and put point inside it."
  (interactive)
  (let ((beg (and (use-region-p) (region-beginning)))
        (end (and (use-region-p) (region-end))))
    (if (not (and beg (string-match-p "[^ \t\n]" (buffer-substring-no-properties beg end))))
        (progn
          (deactivate-mark)
          (insert "@@comment:@@")
          (backward-char 2))
      (let ((text (buffer-substring beg end)))
        (when (string-search "@@" text)
          (user-error "The region contains @@, which would end the comment early"))
        (atomic-change-group
          (goto-char beg)
          (delete-region beg end)
          (insert (sp-org--comment-lines text)))
        (deactivate-mark)))))

(with-eval-after-load 'org
  (define-key org-mode-map (kbd "C-c h") #'sp-org-insert-inline-comment))
#+end_src

** Links and citations inside a comment

Org reads =@@comment:...@@= as one export snippet, whose text is opaque, so a link or a citation written inside it is not a link or a citation for Org.
- #548 made =RET=, clicks and =C-c C-o= open a link inside a comment, with a hook and an advice on =org-return=.
- Citar and Embark showed the same root cause, so the fix is now one level lower and replaces that hook and advice:
  - Embark (=embark-act= on a =[cite:@key]= in a comment) took the key for an email address, because the citar target finders ask =org-element-context= and got the snippet.
  - Inserting a citation with citar inside a comment said "Cannot insert a citation here", because =org-cite--allowed-p= does not accept an export snippet.
- The fix makes =org-element-context= see the objects inside a =comment= snippet, as it does everywhere else.
  - Only when point is inside the text of a snippet with the backend =comment=; everywhere else the original function runs untouched.
  - =sp-org--comment-inner-bounds= returns the start and end of the text between the markers, or nil.
  - =sp-org--comment-object-at-point= parses that text again with =org-element-parse-secondary-string=.
    - Narrowing does not work: =org-element-context= widens the buffer, so it would return the snippet again.
    - The text is parsed as ordinary Org, so links, citations and their references are found by the usual parser.
    - Every position of the parsed links, citations and references is shifted to a real buffer position, so Embark, citar and =org-cite-boundaries= get real bounds.
    - The innermost object that contains point is returned: a =citation-reference= on a key, the =citation= on =[cite:=, a =link= on a link.
  - =org-element-context= is advised with =:around=; calls that pass an element are not touched.
- Everything that asks for the context follows: =C-c C-o= (=org-open-at-point=), =RET= (=org-return= with the strict link rule of =sp-org-point-strictly-in-link-p=), Embark and citar actions.
- Inserting a citation inside the text of a comment: =org-cite--allowed-p= is advised so a comment counts as running text.
  - The inserted =[cite:@key]= keeps its single =@=; only =@@= would end the snippet.
- The font-lock rule now accepts a single =@= inside the comment, so a comment holding a citation is highlighted.
- Links and citations outside comments, and other snippet backends (=@@html:=), are unaffected.

#+begin_src emacs-lisp -i
(defun sp-org--comment-inner-bounds (&optional context)
  "Bounds (BEG . END) of the text of the `@@comment:@@' snippet CONTEXT, or nil.
CONTEXT is the snippet at point, by default as `org-element-context' gives it.
Point must be inside the text."
  (let ((ctx (or context (org-element-context))))
    (when (and (eq (org-element-type ctx) 'export-snippet)
               (equal (org-element-property :back-end ctx) "comment"))
      (let ((beg (+ (org-element-property :begin ctx) (length "@@comment:")))
            (end (- (org-element-property :end ctx)
                    (org-element-property :post-blank ctx)
                    (length "@@"))))
        (and (<= beg (point) end) (cons beg end))))))

(defun sp-org--shift-positions (tree delta)
  "Add DELTA to the position properties of the links and citations of TREE.
The nodes are changed in place."
  (org-element-map tree '(link citation citation-reference)
    (lambda (node)
      (dolist (prop '(:begin :end :contents-begin :contents-end))
        (when-let* ((value (org-element-property prop node)))
          (org-element-put-property node prop (+ value delta)))))))

(defun sp-org--comment-object-at-point (context)
  "Link, citation or citation reference at point inside snippet CONTEXT, or nil.
The result has real buffer positions, like what `org-element-context' returns."
  (when-let* ((bounds (sp-org--comment-inner-bounds context)))
    (let ((tree (org-element-parse-secondary-string
                 (buffer-substring-no-properties (car bounds) (cdr bounds))
                 '(link citation)))
          (delta (1- (car bounds)))
          best)
      (sp-org--shift-positions tree delta)
      (org-element-map tree '(link citation citation-reference)
        (lambda (node)
          (let ((beg (org-element-property :begin node))
                (end (org-element-property :end node)))
            (when (and (<= beg (point)) (< (point) end)
                       (or (null best)
                           (< (- end beg)
                              (- (org-element-property :end best)
                                 (org-element-property :begin best)))))
              (setq best node)))))
      best)))

(define-advice org-element-context (:around (orig &optional element) sp-org-comment-objects)
  "Look inside `@@comment:@@' snippets for links and citations."
  (let ((context (funcall orig element)))
    (or (and (null element) (sp-org--comment-object-at-point context))
        context)))

(define-advice org-cite--allowed-p (:around (orig context) sp-org-comment-text)
  "Allow a citation in the running text of a `@@comment:@@'."
  (or (and (sp-org--comment-inner-bounds context) t)
      (funcall orig context)))
#+end_src

** Other approaches

org-extra-emphasis

*** Creating a link-type or macro approach.

Claude considers this to be more portable
- Define a custom link type that renders as a highlight on export and is fontified in the buffer:

!@the thing is that I don't need this highlighting to be there during the export.

#+begin_src elisp
(org-link-set-parameters
 "hl"
 :face '(:background "yellow" :foreground "black")
 :export (lambda (path desc backend _)
           (let ((text (or desc path)))
             (pcase backend
               ('html  (format "<mark>%s</mark>" text))
               ('latex (format "\\hl{%s}" text))
               (_ text)))))
#+end_src

Usage: [[hl:some text]] or [[hl:id][some text]]. It’s more verbose, but it survives in any Org parser and exports cleanly.

*** Block-level highlighting only

Use #+begin_mark-style special blocks

- For block-level highlighting only. Special blocks export to a <div class="mark">, which you can style with CSS, but this doesn’t work inline.
- My recommendation: keep org-extra-emphasis for inline highlighting in your own notes, and add the custom link type (option 2) only if you need reliable cross-backend export or interoperability with other Org tools. Option 3 is fun but fragile.

*** Using the Markdown syntax instead

If you really want the Markdown look in the buffer, add a font-lock rule:

#+begin_src emacs-lisp :tangle no
(font-lock-add-keywords
 'org-mode
 '(("\\(==\\)\\([^=\n]+\\)\\(==\\)"
    (1 '(face nil invisible org-link) t)
    (2 '(:background "yellow" :foreground "black") t)
    (3 '(face nil invisible org-link) t))))
#+end_src

This only affects display. Export won’t understand it unless you also add an ~org-export-filter-plain-text-functions~ hook to convert ==text== to <mark> etc. Also note that it clashes with Org’s =verbatim= when text sits next to =, so it can misfire on things like =foo==bar=.

**** Inherit from a theme face (simplest)

An inheriting face updates automatically when you switch themes, with no hooks needed:

#+begin_src elisp :tangle no
(defface my-org-inline-comment
  '((t :inherit secondary-selection))
  "Face for @@comment:...@@ inline comments.")
#+end_src

Good candidates to inherit from are =secondary-selection=, =highlight=, =region=, and =lazy-highlight=. Every decent theme styles these to be visible but not clashing, so try a few and pick the one you like.

**** Derive the colors from the theme (more tailored)

If you want the comment’s own hue (so it matches how your theme already renders comments) with a subtle tinted background, compute it from the current theme’s colors and recompute whenever the theme changes:

#+begin_src elisp :tangle no
(require 'color)

(defun my-blend-colors (c1 c2 alpha)
  "Blend C1 into C2; ALPHA is the weight of C1 (0-1)."
  (let ((a (color-name-to-rgb c1))
        (b (color-name-to-rgb c2)))
    (apply #'color-rgb-to-hex
           (append (cl-mapcar (lambda (x y) (+ (* alpha x) (* (- 1 alpha) y)))
                              a b)
                   '(2)))))

(defface my-org-inline-comment '((t)) "Inline comment face.")

(defun my-update-inline-comment-face (&rest _)
  (let* ((fg (face-attribute 'font-lock-comment-face :foreground nil 'default))
         (bg (face-attribute 'default :background nil 'default)))
    (set-face-attribute 'my-org-inline-comment nil
                        :foreground fg
                        :background (my-blend-colors fg bg 0.18)
                        :slant 'normal)))

(my-update-inline-comment-face)
(add-hook 'enable-theme-functions #'my-update-inline-comment-face)
#+end_src

The 0.18 controls how strong the tint is. Raise it for a bolder highlight, lower it for something subtler. Because the background is a blend of the comment color and your theme’s background, it works in both light and dark themes.
