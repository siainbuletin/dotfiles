This module makes Emacs see the same environment as a login shell, which matters mostly on macOS where GUI apps do not inherit the shell's =PATH=. It uses =exec-path-from-shell=, configured after John Wiegley's setup.

Also in this module:

- a commented-out alternative from the modular configuration it was originally based on,
- a command for piping the region through a shell command,
- =inheritenv=, installed for the Claude Code setup in =sp-ai=,

The commentary notes that Windows and Linux still need their own solution.

The commentary at the top of the module says:

#+begin_quote
This prefers using the exec-path-from-shell package in order to deal with all the
binaries that macOS has to pull.

There needs to be a separate solution for Windows and Linux, respectively, so these
packages don't get used on every system in part.

The folders my files live in (notes, bibliography, checkouts) are named in
`sp-globals' and can be overridden by SP_* environment variables.  Those are read
when `sp-globals' loads, which is before the shell's environment is imported
below, so a GUI Emacs only sees them when it is started from a shell (or when
they are set for the graphical session).  Nothing here changes those folders.
#+end_quote

* Overview

** Header and commentary

The commentary explains the reliance on =exec-path-from-shell= for macOS binaries, and that other systems should eventually get separate handling so these packages are not used everywhere.

Paths:

- It also points to =sp-globals=, which names the folders the other modules use (notes, bibliography, source checkouts) and lets =SP_NOTES_DIR= and its siblings override them.
- Those variables are read when =sp-globals= loads, before this module imports the shell's environment. So a graphical Emacs only sees them when started from a shell, or when the graphical session sets them.
- The module requires =sp-globals= so the dependency is explicit. It does not change any of those folders.

* Importing the shell environment

** exec-path-from-shell

=exec-path-from-shell=:

- Only used under graphical window systems (mac, ns, x and pgtk), since a terminal Emacs already inherits the shell environment, and in a daemon, where =window-system= is nil at startup.
- =exec-path-from-shell-initialize= copies =PATH= and =MANPATH=.
- The loop then copies further variables: spelling config, editor, GnuPG and pass locations, SSH agent socket, SSL certificate paths (including the Nix and Node ones) and StarDict data.

#+begin_src emacs-lisp -i
;; This configuration of exec-path-from-shell is taken from John Wiegley
(use-package exec-path-from-shell
  :ensure t
  :if (or (daemonp) (memq window-system '(mac ns x pgtk)))
  :config
  (exec-path-from-shell-initialize)
  (dolist (var '("ASPELL_CONF"
                 "EDITOR"
                 "GNUPGHOME"
                 "NIX_SSL_CERT_FILE"
                 "NODE_EXTRA_CA_CERTS"
                 "PASSWORD_STORE_DIR"
                 "SSH_AUTH_SOCK"
                 "SSL_CERT_FILE"
                 "STARDICT_DATA_DIR"))
    (exec-path-from-shell-copy-env var)))
#+end_src

* Shell commands on text

** Replacing the region with shell output

=sp-replace-with-shell= pipes the region through a shell command.

- Prompts for a shell command, runs it with the region as input, and replaces the region with the output.
- Refuses to run if no mark is set.
- The work happens in a temporary buffer. If the =*Shell Command Output*= buffer did not exist before, it is killed afterwards so no clutter is left behind.
- Unlike the built-in ~C-u M-|~, it hides messages while running.

#+begin_src emacs-lisp -i
(defun sp-replace-with-shell (posBegin posEnd command)
  "Pipe region through shell command and replace"
  (interactive (let (command)
		 (unless (mark)
		   (user-error "The mark is not set now, so there is no region"))
                 (setq command (read-shell-command "Shell command on region: "))
                 (list (region-beginning) (region-end) command)))
  (with-temp-message ""
    (let ((string (buffer-substring-no-properties posBegin posEnd))
          (buffer (current-buffer))
          (shell-output-exists (get-buffer "*Shell Command Output*")))
      (with-temp-buffer
        (insert string)
        (shell-command-on-region (point-min) (point-max) command (current-buffer) t)
        (setq string (buffer-substring-no-properties (point-min) (point-max))))
      (delete-region posBegin posEnd)
      (insert string)
      ;; If *Shell Command Output* wasn't opened before, kill it
      (unless shell-output-exists
        (let ((output-buffer (get-buffer "*Shell Command Output*")))
          (when output-buffer
            (kill-buffer output-buffer)))))))
#+end_src

* Support for other modules

** inheritenv

The comment credits a blog post on Claude Code in Emacs and points at =sp-terminal=. =inheritenv= makes processes started from a buffer inherit that buffer's environment, which =claude-code= in =sp-ai= waits for.

Known bug:

- The recipe is given with =:straight=, but this config uses Elpaca, not straight.el.
- =use-package= does not recognise that keyword, so it most likely reports a parse error and does not install inheritenv.
- =claude-code= is declared =:after= inheritenv, so it would then never be configured.
- Replacing =:straight= with =:ensure= and the same recipe would fix this.

#+begin_src emacs-lisp -i
;;;; Recommended in https://blog.dornea.nu/2026/04/23/claude-code-customizations-in-emacs/ for getting a terminal backend in Emacs. See also sp-terminal.el
(use-package inheritenv
  :ensure t)
#+end_src
