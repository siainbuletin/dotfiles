Follow-up to #24 (merged).

*Before:* =emacs-pr= gave all sandboxes one shared =elpaca= folder and one shared notes copy, so only one sandbox could safely run at a time, and a sandbox could only be started from a shell.

*After:*

- Each PR gets its own =var/elpaca=, an APFS clone of a seed that is itself a clone of the live =var/elpaca=, and its own =HOME= with a clone of =~/notes= (=~/.cache/emacs-sandbox/home/pr-N=). Any number of sandboxes can run at once, next to the live Emacs. Only the native-compile cache is still shared, which Emacs supports. =emacs-pr rm N= deletes everything of a PR, =emacs-pr reset N= refreshes its notes, and =emacs-pr reseed= drops the seed.
- A new module, =sp-sandbox=, adds =M-x sp-sandbox-pr= (the number defaults to the =22= or =#22= at point), =sp-sandbox-remove=, =sp-sandbox-reset-notes= and =sp-sandbox-reseed=. They run the fish function in a separate process from the Emacs you are working in and show its output in =*emacs-pr*=.
- The README section "Testing a pull request in a sandbox" describes the new layout and the commands. Chemacs2 is not needed: =--init-directory= already gives each worktree its own packages, and the isolation comes from the per-PR =HOME= and clones, which a Chemacs2 profile would not provide.

*How it was checked:* the function passes =fish -n=. I ran it against a local stand-in for the yadm repository, with stub =emacs= and =cp=, for two PRs, a re-run and =rm=. Each PR's build symlinks pointed into its own =elpaca=, each got its own home, and =rm= removed one without touching the other. The Emacs commands were run in batch against a stub =emacs-pr= (arguments, output buffer, number at point), and =sp-sandbox.org= tangles to =sp-sandbox.el= identically in Emacs 29.3. I did not run any of this with real yadm, Emacs or APFS, so the first real launch on the Mac is the test.
