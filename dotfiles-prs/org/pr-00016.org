*Before:* =sp-vulpea-hierarchy= knew one relation, =parent=, read from one metadata key (=vulpea-hierarchy-parent-key=).

*After:* =vulpea-hierarchy-relations= declares any number of relations. Each has a label, a colour and a list of sources: a metadata key (=- supports :: [[id:..][..]]=), the inverse of a metadata key (=- children ::= on a parent gives its children their parent edge), or a file property such as =DG_SUPPORTS= (and the inverse of a property). =parent= still builds the tree; =supports=, =opposes=, =informs= and =answers= are declared as defaults, the same names =discourse-graphs= uses. The other relations appear as dashed, labelled, coloured links between two notes that are both in view, in the browser page (with a legend) and in the SVG export. The outlines are unchanged. =vulpea-hierarchy-parent-key= is removed: its value is now the =parent= relation's =(meta "parents")= source.

*How:* =vulpea-hierarchy--edges= reads every source into =(subject relation object)= edges and drops duplicates; =--build= turns =parent= edges into the tree and keeps the rest as =:links=; =--scope= keeps the links whose two ends are in scope. Tested on mock notes with a file property, an inverse key, a repeated key and a comma-separated key, plus a JavaScript syntax check, =dot=, and a headless Chromium screenshot. Property sources have to test every note, because vulpea has no property index. Not run against your real vault, and I did not check how vulpea fills =vulpea-note-properties= there, so please confirm =DG_SUPPORTS= links show up. The literate doc is regenerated and tangles back byte for byte.

The links are drawn between boxes without choosing where they sit; placing them by direction is the follow-up PR in this stack.
