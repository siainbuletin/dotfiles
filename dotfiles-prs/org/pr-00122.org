** Description
/Requested by *Sia*/

*Reported:* since #119, opening any prompt with =M-x= hangs Emacs completely on macOS (=C-g= pressed many times eventually shows =[quit]=). Setting =(setq mini-frame-resize 'not-set)= at the end of =sp-mini-frame.el= changed nothing.

*Cause (a guess, not reproduced):* #119 made the frame start at one line (=(height . 1)=), placed it with a computed pixel =top=, set =mini-frame-resize= to =t= and changed the border faces of the open frame on every showing. Since =not-set= did not help, the loop is probably in the frame being resized or restyled while open with a one-line height, which Vertico then needs to be much taller.

*Change:* the pre-#119 pattern with a fixed size:

- =mini-frame-resize= is =not-set= again; no resizing code, no =mini-frame-resize-max-height=.
- =(height . N)= with N = =vertico-count= + prompt + divider line, =(left . 0.5)=, =(top . 0.5)= (fractions: centred horizontally and vertically); width =0.6= as before.
- No =set-face-background= on the open frame; the border colour is set with =mini-frame-internal-border-color= and applies when the frame is made.
- Colours from the =default= face (#121), 4 pixels padding (#119) unchanged.

*Trade-off:* with fewer than =vertico-count= candidates the frame keeps its size and has empty space at the bottom.

*Not tested:* nothing was run in Emacs, so I cannot confirm this stops the hang. If it still hangs, the next things to try are =(setq sp-mini-frame-divider-char nil)= (removes the overlay) and starting Emacs with =--debug-init= plus =M-x toggle-debug-on-quit= before pressing =M-x=, which shows where it loops.
