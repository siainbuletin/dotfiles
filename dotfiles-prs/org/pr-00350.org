** Description
Follows #340 and #341. =gh-pr-pdf= fetched every pull request again on every run. After the first run it now asks =github-backup= for only what changed.

**** Changes
:PROPERTIES:
:CUSTOM_ID: changes
:END:
All in =gh-pr-pdf/= (script and =README.org=, which has a new "Running it again" section).

- Fetching: the script always passes =github-backup -i=. The first run has no checkpoints, so it fetches everything and =github-backup= writes them. Later runs request only new data since the last successful backup.
- =backup/.gh-pr-pdf-state.json= records the last full fetch, the options it used and a hash per rendered pull request. A failed fetch does not move it forward.
- A full fetch is forced:
  - when no earlier one is recorded, or with =--full=;
  - when the options differ from the last run, because =-i= does not backfill a flag that is new;
  - when the last full fetch is older than =--full-every DAYS= (30 by default, 0 turns it off). The =github-backup= documentation warns that a failed earlier run can leave a gap in an incremental backup; this is the cure.
  - A full fetch first deletes =github-backup='s own checkpoint files (=last_update=, =reviews_last_update=) in =backup/=, so it is not cut short by an older checkpoint.
- Rendering: an org file is rebuilt only when the JSON of its pull request changed (or the renderer did), since =pandoc= runs several times per pull request. Org files of pull requests that vanish from the backup are removed. The PDF is still built from all the org files, a local step that does not use the API.
- Discussions stay a full fetch each time (one query per 25 discussions).
- The progress line says which mode ran and why, for example =fetching pull requests: incremental (last full fetch 3 days ago, ...)=.

**** Not run
:PROPERTIES:
:CUSTOM_ID: not-run
:END:
=github-backup= is not installed in the container and there is no way to install it, so the incremental mode was run against a stand-in that logs how it is called and writes checkpoint files the way its documentation describes. Covered: first run, an unchanged rerun (0 rendered, 3 unchanged), one changed pull request (1 rendered), =--full= (checkpoints deleted first), changed options, a 40-day-old state against 29 days, =--full-every 0=, a failed fetch (state unchanged), a pull request that vanishes, and a corrupt state file.

Not seen, and worth checking on a real run:

- How =github-backup= applies =-i= to pull requests, and whether it fetches the comments and commits of one that changed (the PyPI page only says that it requests new data since the last successful backup).
- That it fetches everything when it finds no checkpoint, which the first run and every full fetch rely on.
- Quick check: compare the API requests of the second run with the first (=gh api rate_limit= before and after).

=typst compile= is still not run in the container either (see #341).
