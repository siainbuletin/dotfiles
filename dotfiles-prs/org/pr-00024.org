/Requested by *Sia* · [[https://claude.ai/code/project/chan_01KaQfLZaF43QUMN3kcT7pW2?thread=cmsg_01KaQfLZaF43QUMN3kcT7pW22ykMMYap3WBMUhHviqhAoA][project thread]]/

*Before:* testing a pull request of the Emacs config meant checking its branch out in =~= and restarting Emacs, and a PR could write to the real notes.

*After:* the fish function =emacs-pr N= (in =.config/fish/functions/emacs-pr.fish=) fetches =pull/N/head= through yadm into a detached worktree at =~/src/dotfiles-wt/pr-N= and starts a second Emacs on it with =--init-directory=. That Emacs runs with =HOME= set to a throwaway folder holding an APFS copy of =~/notes=, so the PR cannot change the real notes. All sandboxes share one package cache, cloned from your live =var/elpaca= (with elpaca's absolute build symlinks repointed), so no PR reinstalls packages it already has. =emacs-pr rm N=, =emacs-pr reset= and =emacs-pr reseed= clean up. The new README section "Testing a pull request in a sandbox" documents usage, what it does, what is not isolated, and what to do when something fails.

*How it was checked:* the function passes =fish -n=, and I ran it against a local stand-in for the yadm repository, with stub =emacs= and =cp=, to check the fetch, the worktree creation and re-run, the sandbox home, the cache clone, the symlink repointing and the launch arguments. It was not run with real yadm, Emacs or APFS (this container is Linux), so the first real run on the Mac is the test.
