/Requested by *Sia* · [[https://claude.ai/code/project/chan_01KaQfLZaF43QUMN3kcT7pW2?thread=cmsg_01KaQfLZaF43QUMN3kcT7pW2CeT7EXLucCBx8drQGW8YWR][project thread]]/

Before: there was no place to track code issues, and working on a dotfiles branch meant checking it out in =~=, which swaps the live config.

After: =M-x sp-org-issues-create-area= creates an "Issues" file as a vulpea-para area (tagged =area=, in the vulpea database), with one heading per repository (dotfiles, vulpea-mcp). =C-c c I= files an issue under a repository, =C-c o a i i= shows an issue board (in progress, next, waiting, open), and =M-x sp-org-issues-start= gives an issue its own git worktree under =~/src/dotfiles-wt/= and opens Magit there. For the dotfiles the worktree is added from the yadm repository itself, so =~= is never touched.

How: the file sets the org-gtd keywords (=TODO NEXT PROG WAIT | DONE CNCL=) with its own =#+todo:= line, and every issue carries =ORG_GTD: Actions=, so a NEXT issue also shows in =org-gtd-engage=. Repository settings (=GIT_DIR=, =WORKTREE_ROOT=, =BASE=) sit on the repository heading and are inherited by the issues. The module requires =sp-vulpea-para= first and appends its capture template and agenda commands, so that module's =setq= cannot wipe them. Closing an issue offers to remove its worktree, and Magit lists untracked files in yadm worktrees (the yadm repo hides them for =~=). =init.el= loads it right after =sp-org-ext=.

The literate source is =docs/tangles/sp-org-issues.org=; it tangles back to the =.el= byte for byte. Tested in batch Emacs with Org and current Magit against a repository laid out like yadm's (vulpea calls stubbed): area creation, capture into an existing and a missing repository heading, both agenda views, starting an issue from the agenda (branch, worktree, PROG), and removing the worktree on DONE.
