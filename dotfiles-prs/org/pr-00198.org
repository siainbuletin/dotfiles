**** What
:PROPERTIES:
:CUSTOM_ID: what
:END:
=tools/quick-capture-native= no longer waits for Emacs. It now:

1. asks for the line in the macOS dialog (or takes it as an argument, skipping the dialog),
2. writes it atomically to a spool folder (=~/.local/state/quick-capture=, override with =QUICK_CAPTURE_SPOOL=),
3. pokes Emacs in the background with =emacsclient -n -e '(sp-quick-capture-drain)'= and returns.

=sp-quick-capture-drain= (new) files the queued lines oldest first and deletes each file. It runs on the poke, 2 seconds after the module loads (lines captured while Emacs was down), and after =sp-quick-capture-drain-interval= (30) idle seconds. Failures go to =failed/= in the spool. The file's mtime is the capture time, used for =:CREATED:= and for relative dates (=!tom=), so a line filed days later still means what you meant.

**** Why this approach
:PROPERTIES:
:CUSTOM_ID: why-this-approach
:END:
Before, =emacsclient -e= blocked while Emacs was busy and the line was lost when Emacs was not running. A spool file keeps the task safe on disk and needs no extra tool: AppleScript and bash are already used, and Hammerspoon, Shortcuts, Alfred or Raycast can call the script (with an argument, if they have their own input box). Writing straight into =inbox.org= from bash was rejected: it would race with the open Emacs buffer and duplicate the parser.

**** Tests
:PROPERTIES:
:CUSTOM_ID: tests
:END:
- 4 new ERT tests (capture time, ordering, partial files ignored, failures parked, no spool); all 13 pass in Emacs 29.3 batch.
- Real daemon on Linux: with the daemon stopped (=SIGSTOP=) the script returns in 0.02 s and the line is filed on resume. Plain =emacsclient -n= did hang for 15 s on a stopped daemon, which is why the poke runs in the background. With the daemon dead the line stays queued.
- Not run on macOS (dialog, notifications, hotkey launchers).

The module is tangled from =docs/tangles/text/sp-quick-capture.org=; CHANGELOG entry is in the Quick capture set.
