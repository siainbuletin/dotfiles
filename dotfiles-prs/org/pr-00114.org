Adapted from Nicolas Rougier's =nano-modeline.el= and =nano-minibuffer.el= (N Λ N O, GPLv3).

*What changes*

- New =sp-nano-style= (tooling), shared by =sp-lambda-modeline= and =sp-prot-modeline= (both call =sp-nano-style-install=):
  - *Header line* in nano's blocky style: a block with =RW= (writable, muted), =RO= (read-only, warning colour) or =**= (modified, error colour; =--= for a dedicated window), then the path of the file in bold and the project name at the right edge. Other windows get a muted block and path. Colours come from the theme (=warning=, =error=, =shadow=, inverted). The project name is cached per buffer.
  - *Divider* between the text of the buffer and the mode line: a thin overline in the =shadow= colour on =mode-line=, =mode-line-inactive= and the lambda-line faces, set again after each theme load (=sp-nano-style-divider= turns it off). The mode line itself stays whole (nano shrinks its own to the divider; not done here, as you asked for a real mode line).
- The header code that was in =sp-lambda-modeline= (and Prot's path construct) is replaced by this module.
- =sp-mini-frame=: =M-x= (=sp-mini-frame-nano-commands=) opens at the bottom as in =nano-minibuffer= (full width, 5 lines, 12 px fringes, no border, background moved 8% from the theme's, a half-height blank line above the prompt). Other prompts keep the centred frame and dimming.
- Docs, docs index and CHANGELOG updated; the docs tangle to the =.el= files.

*Interpretation to confirm:* I read "the =M-x= menu beautification" as nano's =mini-frame= styling in =nano-minibuffer.el=. If you meant =nano-command-x= (a prompt drawn in the header line, in =nano-command.el=), say so and I will add that instead.

*Not tested:* nothing was run (no Emacs in the container; the =.el= files were only paren-balanced by script). To check in Emacs 31: block colours in your themes, the divider above both mode lines, the =M-x= frame at the bottom and its background (=color-blend= is used for it).
