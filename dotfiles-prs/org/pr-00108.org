**** What changes
:PROPERTIES:
:CUSTOM_ID: what-changes
:END:
- With =sp-tag-emoji-mode= on, =vulpea-select-describe-fn= is =sp-tag-emoji-describe-note=: the emoji of the note's tags, then the title (=vulpea-select=, =vulpea-find=, =vulpea-insert=). It depends on the note alone, so vulpea's candidate cache stays valid; the previous value (now =vulpea-select-describe-outline-full= from =sp-vulpea-base=) is restored when the mode is turned off.
- =sp-select-note= is my own selector (same keywords as =vulpea-select=) built on =vulpea-select-from=: the tags in a column at the right edge (=(space :align-to (- right N))=, =N= a fraction of the frame width), small and dimmed, still matchable.
- =sp-insert-note= is =vulpea-insert= with the same emoji and tag column; the link text stays the plain title.
- Both bypass vulpea's candidate cache while they run (the column width is not a property of the note).
- *Callers now use them*, for one look everywhere: =sp-org-create-note-and-link= (its "insert existing" branch) and the wikilink conversion, =sp-tab-inbox=, =sp-move-region-to-heading=, the graph start note in =sp-graphs=, and =sp-collec-query-select-note= (which also no longer confuses same-titled notes). Each of those modules now requires =sp-tag-emoji=.
- Rules can opt out of the selector with =:select nil=. =sp-tag-emoji-select-visit= is not part of this PR.
- Docs and CHANGELOG follow.

**** Worth checking
:PROPERTIES:
:CUSTOM_ID: worth-checking
:END:
=sp-org-create-note-and-link= used to call =vulpea-insert= with two positional functions. Upstream =vulpea-insert= takes keywords (=:filter-fn=, =:create-fn=), so the call now uses keywords; if your installed vulpea still has the positional signature, that call needs to go back.
