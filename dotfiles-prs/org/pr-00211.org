**** Summary
:PROPERTIES:
:CUSTOM_ID: summary
:END:
The dashboard read every agenda file through Org at each start and redraw. It now keeps each file's open TODOs in =sp-cache-dir= (=dashboard-entries.eld=), keyed by path + mtime + size.

- Only new or changed files are read at start; deleted files are dropped; the cache is dropped when =org-todo-keywords= changes.
- Deadline/scheduled are cached as absolute days and made relative on read, so they do not go stale overnight.
- A changed file is read from disk in a temp buffer (no mode hooks, nothing left open): =org-map-entries= on a file name reuses an open buffer, which could put an older version in the cache. A buffer with unsaved edits is read instead and not cached.
- The per-draw =sp-dashboard--entries-cache= and the public/private filtering in =sp-dashboard--todos= are unchanged.
- Message: =[dashboard] read 100 agenda files: 99 cached, 1 re-read, in 0.01s=.
- =M-x sp-dashboard-clear-entries-cache= resets it.

**** Findings
:PROPERTIES:
:CUSTOM_ID: findings
:END:
*Coverage (100 agenda files from the running Emacs).* =org-map-entries= finds 362 keyword headings (339 open, 23 done). org-ql =(todo)= finds the same 339 plus 3 TODOs under a =* Archive :ARCHIVE:= heading, which the dashboard skips on purpose; with =(not (tags "ARCHIVE"))= the two match exactly. The file with its own =#+TODO: OPEN | ANSWERED= is read correctly by both. vulpea.db has only 35 todo rows (it indexes only headings with an ID), so it cannot be the source.

*Engine speed.* org-ql is not meaningfully faster: cold 2.5--3.4 s against 2.5--2.9 s for =org-map-entries=, almost all of it visiting the files. Warm it was 0.02--0.04 s against 0.05--0.07 s, possibly its own cache. The cache therefore keeps =org-map-entries= (no extra package).
