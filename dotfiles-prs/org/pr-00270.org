/Requested by *Sia* · [[https://claude.ai/code/project/chan_01KaQfLZaF43QUMN3kcT7pW2?thread=cmsg_01KaQfLZaF43QUMN3kcT7pW2NidJm7Tzd128tJp4sbpQtK][project thread]]/

Found while looking for the Emacs start-up hang. In a batch profile of a copy of the real vault and =vulpea.db=, 56% of the CPU over 145 s was =vulpea-select-cache-prewarm-step=, which reads every row of the database into a candidate cache for =vulpea-find= and =vulpea-insert= as soon as =vulpea-db-autosync-mode= starts (500-note chunks on the main thread; =vulpea-select.el= lines 547 and 1036 to 1092).

- =(setq vulpea-select-cache-prewarm nil)= in the vulpea base settings. The cache is then built at the first =vulpea-find= or =vulpea-insert=, which pauses once.
- New option =sp-vulpea-autosync-delay= (30 idle seconds, was a fixed 5) for starting autosync.

Org doc edited first, =.el= to match; CHANGELOG entry added. Not run in Emacs (none in the container). The hang is not confirmed fixed: a native sample of the live Emacs also showed =org-element= parsing from the autosync indexing itself.
