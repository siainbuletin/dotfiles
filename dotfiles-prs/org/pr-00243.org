New module =sp-refile= (doc =docs/tangles/funct/sp-refile.org=, tangled =sp-refile.el=) with one command, =sp-refile= (=C-x s t=, =C-c C-w= in Org):

- On a heading it asks "Refile to" with one list: headings of the current note (the =org-refile= case), =[New note: own file]= (calls =sp-split-leave-parents=, so the #240 =- seealso ::= handling is unchanged) or =[Another note...]= (pick a note, then a heading or the top of it).
- Before the first heading (or =C-u C-u=) it merges the whole note under a heading of another note: title becomes the heading, filetags its tags, the =:ID:= stays so links still resolve, then the old file is deleted after confirmation.
- The copy is saved in the target before the source is removed.

Decisions to check:

- =vulpea-merge= is not in this repo or the container's Vulpea, so the merge is built from Org functions only.
- =sp-split-leave-parents= stays as the split engine (code and tests untouched); =sp-refile= requires it. I did not move its 650 lines.
- =C-x s t= now runs =sp-refile= (autoload and binding in =sp-org-base=); =sp-move-region-to-heading= (loose text, =M-a=) is untouched.

Testing: 4 ERT tests (=tests/sp-refile-test.el=) pass in Emacs 29.3 batch with Vulpea/Denote stubbed. The prompts, the split path, merge deletion and the real Vulpea database were not run.
