**** What was slow
:PROPERTIES:
:CUSTOM_ID: what-was-slow
:END:
- Each colour press called =app:getMenuItems()=, which reads the whole DEVONthink menu bar through the macOS accessibility API (every menu, submenu and item, one round trip each). That is the slow part.
- Then it searched the Format menu for the colour, and =selectMenuItem= walked the path again.
- There are no fixed delays (=usleep= or =doAfter=) in the colour path, so the menu-bar read dominates.
- *Not measured.* I cannot run DEVONthink or Hammerspoon from here, so this is from reading the code, not a timing. Use the new benchmark below to see the numbers on your Mac.

**** What changes
:PROPERTIES:
:CUSTOM_ID: what-changes
:END:
- One menu-bar read now finds all seven colour items, and their paths are cached.
- A key press selects the cached path directly, with no menu-bar read.
- The cache is filled about a second after DEVONthink comes to the front, so even the first press is fast.
- If the cached item is not found (for example, a colour renamed), the cache is dropped and the menu is read once again. Behaviour and alerts are the same as before.
- =Cmd+Z= and =Cmd+Shift+Z= are unchanged: their menu titles change with the action, so they cannot be cached. They still read the menu bar on each press.
- New =DEVONthink.benchmark()= in the Hammerspoon console prints how long the menu-bar read takes and how long a cached selection takes.
