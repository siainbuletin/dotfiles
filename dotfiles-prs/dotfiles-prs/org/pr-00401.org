**** What
:PROPERTIES:
:CUSTOM_ID: what
:END:
- =gh-pr-pdf= now starts every PR on a new page in the PDF.
- It no longer fails to build the PDF on PR text where inline code is followed by =.name=.

**** Cause
:PROPERTIES:
:CUSTOM_ID: cause
:END:
- The committed =.typ= (366 PRs, pandoc and Typst 0.15) compiles with every PR, so the org files and that snapshot are fine.
- A fresh re-render of the same backup with pandoc 3.9 failed in =typst compile= with =raw does not have field "el"=.
  - pandoc writes inline code as =#raw("...")=.
  - Typst reads =#raw("...").el= as field access, not as text.
  - PRs #64, #93, #176 and #271 trigger it: their source has nested backticks, so pandoc leaves =.el= or =.gitignore= right after the span.
- The failed compile left the previous PDF in place, so the PDF looked current but lacked the newer PRs, and compiling again fails the same way.
- I could not see Sia's PDF, so this is the cause I reproduced, not a proven match for their exact output.

**** Changes
:PROPERTIES:
:CUSTOM_ID: changes
:END:
- =harden_typst= puts a zero-width space after =#raw(...)= when =.letter= follows. Only =#raw= calls are touched (table code such as =(auto, auto).at(col)= needs its dot).
- The preamble gets =#show heading.where(level: 1)= with a weak =pagebreak=: one PR (or discussion) per page.
- The old PDF is deleted before =typst compile=, so a failure cannot leave a stale one.
- =README.org= documents the three points as bullets.
