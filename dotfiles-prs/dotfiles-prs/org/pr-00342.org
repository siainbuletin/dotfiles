Follow-up to #335 and #338.

**** Problem
:PROPERTIES:
:CUSTOM_ID: problem
:END:
Notes made by the backfill had no Vulpea =:ID:=, no =:CREATED:=, no BibTeX metadata, and the =collection-query-table= block in the book/collection note stayed empty. The likely common cause: the backfill went through =citar-create-note=, and when the =citar-vulpea= source is not the active one citar writes a plain file itself. Such a file never passes through =vulpea-create=, so the =sp-notes= advice (=:CREATED:=) and Vulpea's ID/indexing never ran. The metadata fill and the database update also looked the note up by key instead of by its file, so a miss was only a message.

**** What changes
:PROPERTIES:
:CUSTOM_ID: what-changes
:END:
- New =sp-litnotes-meta-create-note= (option =sp-litnotes-meta-create-function=): makes the note with =vulpea-create= (ID, =litnote= tag, =ROAM_REFS=, =<key>.org= in the litnotes folder, =:CREATED:=), with the title of =sp-litnotes-meta-new-title=.
- Each note is then filled with =sp-litnotes-meta-fill=, given its file explicitly (authors, title, year, =bib-parent=, =bib-project=, read-status, relevance, priority) and tidied.
- The files are put in the Vulpea database one by one, then the table is created or refreshed. If the query table module does not load, that is now reported instead of skipped.
- Literate doc updated (bullets); three new ERT tests.

**** Testing
:PROPERTIES:
:CUSTOM_ID: testing
:END:
- =sp-litnotes-meta= ERT tests pass (16/16, Emacs 29.3, stubbed =vulpea-create=, Vulpea database and author notes). One test runs the real fill and tidy on a stub-made file and checks the ID, =:CREATED:=, title, =pub-author=, =pub-year= and =bib-parent=, and that the file was passed to =vulpea-db-update-file=. =tools/check-tangle.sh= passes.
- Not run with the real Vulpea, citar or vault, and the real table module was not loaded. The cause above is inferred from the symptoms.
