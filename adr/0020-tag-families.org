#+title: 0020 Tag families are an alist of =(FAMILY TAG…)=, turned into Org group tags
#+date: 2026-10-25
#+status: proposed

* Context
The note tags are =org-tag-persistent-alist= in =sp-org-tag-registry.el= (#105), a flat list of 27 tags that is only divided by comments ("People and bodies", "Music", ...). The comments are what I use to think about the tags, but no code can see them. I want /families/ of tags by function (structure, people, music, literature, ...) so that:

- a search for a family finds all its members (=+music= finds =album= and =genre=),
- =sp-org-tag-lint= and =sp-org-tag-add= can talk about families (the tag you add must belong to one),
- =sp-tag-emoji= can give a whole family one emoji or colour, and the tag prompts can list tags by family.

* Decision
The families are data in one *alist whose shape is the one Org itself uses for groups*, =org-tag-groups-alist=: each element is a list whose first string is the family and whose remaining strings are its members.

#+begin_src emacs-lisp :tangle no
(defcustom sp-org-tag-families
  '(("structure"  "area" "project" "agenda" "archive" "cemetery")
    ("who"        "person" "musician" "group" "institution" "company")
    ("music"      "album" "genre")
    ("software"   "software" "package")
    ("literature" "text" "book" "journalarticle" "booksection"
                  "collection" "incollection")
    ("inquiry"    "question" "error" "research-q" "exploratory"))
  "Families of note tags: (FAMILY TAG…).  The source of the tag registry.")
#+end_src

- =sp-org-tag-families= is the only thing I edit. =sp-org-tag-registry.el= keeps its place and its marker line: it sets =sp-org-tag-families=, then derives =org-tag-persistent-alist= from it with =sp-org-tag-families-to-alist=, and =sp-org-tag-add= asks for the family and inserts the tag in that element.
- A member that needs a fast-selection key is a cons, as in =org-tag-alist=: =("group" . ?g)=. A member may itself be the name of another family, which nests them (Org documents this; I did not try it).
- A tag can be in more than one family. A family name is a tag too, so it can be written on a heading, and a family named like one of its members (=software=) should work too (I did not try it).
- Three small functions, all pure and on the alist: =sp-org-tag-families-to-alist= (the Org form below), =sp-org-tag-family-of TAG= (the families of a tag, with nesting) and =sp-org-tag-family-members FAMILY= (its members, with nesting).

Org's form for the same data is the group-tag syntax, which =sp-org-tag-families-to-alist= writes:

#+begin_src emacs-lisp :tangle no
((:startgrouptag) ("music") (:grouptags) ("album") ("genre") (:endgrouptag)
 (:startgrouptag) ("who") (:grouptags) ("person") ("group" . ?g) (:endgrouptag))
#+end_src

With that in =org-tag-persistent-alist=, Org builds the groups itself, so a tag match on a family expands to its members and the completion lists the group.

** Why this is the most Lisp-native shape
- It is a plain alist of lists: =assoc=, =mapcar= and =seq-filter= are the whole API. There is no struct, no hash table and no new macro.
- It is already Org's own representation: =org-tag-alist-to-groups= turns the group-tag form into exactly this alist, and =org-tag-groups-alist= has the same shape. Going the other way is a ten-line loop, so there is one source and Org's variable is derived, never kept in step by hand.
- It reads like the comments in the registry did, so moving the existing tags in is a copy, not a redesign.
- Keys are strings, not symbols, because tags are strings in Org and may contain =@=, =#= or digits; a symbol would need conversion at every use.

** What was verified
In Emacs 29.3 (Org 9.6), headless:

- A =sp-org-tag-families=-shaped list converted to the group-tag form, and =org-tag-alist-to-groups= returned the original families, including the =("group" . ?g)= member (its key survived as a cons).
- In an Org buffer with that alist as =org-tag-persistent-alist=, =org-tag-groups-alist= was set to the families and =org-map-entries= with =+music= found the heading tagged =album=; =+who|+structure= found the headings tagged =person= and =project=.

* Alternatives considered
- *Write the group-tag syntax straight into =org-tag-persistent-alist=.* It is native and needs no code, but "which family is this tag in?" means walking a flat list with keyword markers, adding a tag means finding the right =:grouptags= span, and =sp-org-tag-add= with its marker line cannot place a tag in a family. Kept as the derived form, not the source.
- *A plist per family* (=(music :doc "…" :tags ("album" "genre"))=). It leaves room for a docstring, colour and emoji per family, but it is a second shape next to Org's and nothing needs it yet. Emoji and colour belong to =sp-tag-emoji-rules=, which can take a family as its key (below).
- *A hash table or =cl-defstruct= per family.* More API for the same data, and neither prints nor edits as readably as a quoted list.
- *Nested tag names* (=music/album=, as in Obsidian). Org tags may not contain =/=, so it would need a separator the tag syntax allows (=music_album=), which then matches as one different tag.
- *Properties on the family notes in the vulpea database.* The tags would depend on the database being up; the registry has to work without it (the lint runs on the files).
- *Symbol properties* (=(put 'album 'family 'music)=). Hidden state with no list to read; not editable in one place.

* Consequences
- =sp-org-tag-lint= can report the family of an unregistered tag's likely typo, and tags that are in no family.
- =sp-tag-emoji-rules= can take a family in place of a tag, for example =((family . "music") :emoji "🎵")=, matching when the note has any member. Its combination logic (a more specific rule uses up its tags) would apply unchanged; this is not built yet.
- The tag prompts can sort candidates by family (=group-function= in the completion metadata).
- The task tags in =org-tag-alist= (=@home=, =deep=, ...) can use the same shape and function: one more variable, =sp-org-task-tag-families=.
- Changing a family means editing =sp-org-tag-families=; reloading the registry rebuilds the Org alist.
- The existing registry file would be rewritten to this shape: its comment headings become the family names, so nothing is lost.
- /Untested/: the =sp-org-tag-families-to-alist= and =sp-org-tag-family-of= functions are written only as a sketch here (the conversion above was run); I have not checked how =org-ql= or vulpea queries treat group tags (Org's own tag matching does expand them), nor the completion grouping on my Mac.

* Open questions
- Family names: the six above are my reading of the existing comments; "who" for people and bodies and "inquiry" are the least obvious.
- Whether a tag in no family is allowed (the lint warns) or refused by =sp-org-tag-add=.
