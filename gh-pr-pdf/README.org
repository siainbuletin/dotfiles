#+title: gh-pr-pdf

Turns the pull requests of a GitHub repository (and, if asked, its Discussions) into one org file per pull request, then into one paginated PDF, so that the history of a codebase can be searched as plain text with =rg=, Emacs or =pdfgrep=. Stow links the script to =~/.local/bin/gh-pr-pdf=, so =~/.local/bin= must be on =PATH=.

* What it makes

#+begin_example
gh-pr-pdf siainbuletin/dotfiles
#+end_example

writes =./dotfiles-prs/= with:

- =backup/=: the raw JSON from =github-backup=, kept so that =--skip-fetch= can render again without the network.
- =org/pr-00012.org=, ...: one file per pull request, in number order, plus =all.org= with all of them. Each has a property drawer (=:PR_NUMBER:=, =:STATE:=, =:AUTHOR:=, =:URL:=) for org-ql, and the description, conversation, reviews, inline review comments (with their diff hunk) and the commit list. Every commit is a link to =https://github.com/OWNER/REPO/commit/<sha>=.
- =dotfiles-prs.pdf=: the same text, paginated, with a table of contents of the pull requests and clickable links. The Typst source (=.typ=) stays next to it.

** Options: 
- =--discussions= (also fetch Discussions), 
- =--skip-fetch= (render from =backup/=),
- =--full= (fetch everything again, not only what changed),
- =--full-every DAYS= (also do that when the last full fetch is this old; 30 by default, 0 turns it off),
- =--no-pdf= (org files only),
- =--per-pdf N= (several PDFs of N items), 
- =--reverse= (newest first), 
- =--private= (private repository), 
- =-o DIR= (output folder).

* Running it again

The first run fetches everything. Later runs ask =github-backup= for only what changed (its =-i= option), render again only the pull requests whose JSON changed, and then rebuild the PDF from all the org files. The last step is local and does not use the API, so the PDF is always complete.

- =backup/.gh-pr-pdf-state.json= records when the last full fetch was, which options it used, and a hash of each rendered pull request.
- A full fetch is forced by =--full=, when the options differ from the last run (=-i= does not backfill a flag that is new), and when the last full fetch is older than =--full-every= days. The =github-backup= documentation warns that a failed earlier run can leave a gap in an incremental backup; the periodic full fetch is the cure.
- A full fetch first deletes =github-backup='s own checkpoint files (=last_update=, =reviews_last_update=) in =backup/=, so the next incremental run starts from the full fetch and not from an older checkpoint.
- A failed fetch does not move the state forward.
- With =--discussions=, discussions are fetched in full every time. That is one query per 25 discussions.

* Needs

- =github-backup= (=pipx install github-backup=) and =gh= logged in (=gh auth login=); the token is taken from =gh=.
- =pandoc= 3.1.2 or newer (it has to write Typst) and =typst=.

I believe =typst= and =pandoc-cli= are in the official Arch repositories; check with =pacman -Ss=. Without =typst= the script still writes the org files and the =.typ= file and says so.

* Safety

Pull request text comes from other people. Raw HTML is dropped, =pandoc= runs with =--sandbox= (so an =#+INCLUDE:= line cannot read a file), and lines that start with an org directive are turned into literal text.

Text that Typst reads as code is escaped too: =@key= (a reference: "label =<key>= does not exist"), =$...$= (math) and =<key>= (a label). =pandoc= does not escape these the same way in every version, so the script swaps them for placeholders before =pandoc= and turns them into Typst escapes afterwards; fenced and inline code stay as written. Dollar signs are also kept literal in Markdown bodies, since otherwise =$HOME/$PATH= turns into a math fragment. If an unescaped =@name= is still left in the Typst source, the script warns with the line numbers.

* Inline code followed by a dot

- pandoc writes inline code as =#raw("...")=.
- Typst reads =#raw("...").el= as field access on that element and stops with "raw does not have field el".
- That happens when the source text has odd backticks (for example a code span nested in a code span), so pandoc leaves =.el= right after the span.
- The script puts a zero-width space after =#raw(...)= when a dot and a letter follow, so the text stays text.
- Only =#raw= calls are touched: table code like =(auto, auto).at(col)= needs its dot.

* Page per pull request

- Every level-1 heading in the Typst source is one pull request (or discussion).
- The preamble has =#show heading.where(level: 1)= with a weak =pagebreak=, so each one starts on a new page.
- Weak: no blank page when the heading already starts one.

* Stale PDF

- Before =typst compile=, the script deletes the old PDF.
- A failed compile then leaves no older PDF that looks current (and lacks the newer pull requests).

* Not run

Written in a container without a Mac or a Linux desktop, without Typst and without network access to GitHub's API. What was run: the org and Typst-source output on made-up JSON, including headings in bodies, empty bodies, an injected =#+INCLUDE:= and the splitting into several PDFs. Not run:

- =typst compile= in this container. A first run elsewhere failed on =@key= in a title and a commit message; the escaping above is the fix, checked on made-up JSON and with a scanner for leftover references, but not by compiling again.
- =github-backup= against a real repository. The JSON key names the script reads (=comment_regular_data=, =comment_data=, =review_data=, =commit_data=) match the =github-backup= page on PyPI, which mentions =commit_data= only in passing; they have not been checked against real output. If a pull request reports commits but no list is found, the script prints the keys it did see, and the fix is the key names in =render_pr=.
- The incremental mode against the real =github-backup=. Its decisions (full or incremental, deleting the checkpoints, the state file, which pull requests are rendered again) were run against a stand-in that records how it is called, including a failed fetch, changed options, a pull request that disappears and a corrupt state file. Not seen: how =github-backup= applies =-i= to pull requests, whether it fetches the comments and commits of a pull request that changed, and that it fetches everything when it finds no checkpoint (the PyPI page says it only requests new data since the last successful backup). The first thing to check on a real run is the number of API requests for the second run against the first.
- The Discussions fetch (=gh api graphql=). It reads up to 100 comments and 50 replies per discussion and warns when there are more.
