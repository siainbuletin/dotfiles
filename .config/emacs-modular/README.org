#+title: Sia's modular Emacs configuration

This is a modular Emacs configuration: =init.el= loads sub-libraries from =libraries/modules/=, and each module has a literate Org source in =docs/tangles/=, in subdirectories that mirror those of =libraries/modules/=. The root of the literate configuration is [[file:docs/main.org][docs/main.org]], which has a tree of all the modules after its preamble.

* Tangling the literate files

Nearly every module in =libraries/modules/= has a literate source in the matching subdirectory of =docs/tangles/= (the module tree marks the ones that don't yet): the module =libraries/modules/ui/sp-x.el= is written from =docs/tangles/ui/sp-x.org= (and =lem-dashboard.el= from =sp-lem-dashboard.org=). Older notes with no module of their own, such as =org-config.org=, stay at the top of =docs/tangles/=. The modules are grouped by directory in the module tree of [[file:docs/main.org::*Module tree][docs/main.org]].

** Where a file tangles to

The file header of each literate source says where it tangles (a few documents that write several modules do it per heading, see below). Its second line is a =#+PROPERTY= line like this one, from =docs/tangles/media/sp-ai.org=:

#+begin_example
#+PROPERTY: header-args:emacs-lisp :tangle ../../../libraries/modules/media/sp-ai.el :comments no :padline yes :noweb no :mkdirp yes
#+end_example

- =:tangle= is the path of the =.el= file, relative to the =.org= file. 
  - Every =emacs-lisp= block in the file goes there, in order, unless the block says otherwise.
- =:comments no= keeps Org from adding link comments to the =.el= file
- =:padline yes= puts one blank line between blocks, so tangling reproduces the module as it is.
- =:mkdirp yes= creates the module's directory if it is missing.

A few documents write more than one module. =docs/tangles/text/sp-org-agenda.org= writes both =sp-org-agenda.el= and =sp-agenda-views.el=, so it has no file-wide =#+PROPERTY= line for =:tangle=. Each of its top-level headings carries the same settings in a property drawer instead, as =:header-args:emacs-lisp:= with its own =:tangle= path, and the blocks under a heading go to that heading's file:

#+begin_example
,* Agenda views module
:PROPERTIES:
:header-args:emacs-lisp: :tangle ../../../libraries/modules/text/sp-agenda-views.el :comments no :padline yes :noweb no :mkdirp yes
:END:
#+end_example

Tangling such a document (=C-c C-v t=) writes all of its files, and the tangle-all commands below pick it up because its drawers contain the same =:tangle= path. To add a block to the second module, put it under a heading with the second path.

Blocks with =:tangle no=, such as the ones under a =Sandbox= heading, are for trying configuration out with =C-c C-c= and never reach the =.el= file. To adopt something from the sandbox, move it into a block without =:tangle no=.

** Tangling one file

Open the literate source and press =C-c C-v t= (=org-babel-tangle=). This rewrites the =.el= file named in the header from the blocks in the file; nothing is tangled unless you run it. If you just edited the =#+PROPERTY= line, press =C-c C-c= on it first so Org picks up the change.

** Tangling everything

To rewrite every module at once, evaluate this block with =C-c C-c=. It tangles each literate source whose header points into =libraries/modules/=, and skips the older documents in =docs/tangles/= (the =-old.org= files and the notes that tangle elsewhere).

#+begin_src emacs-lisp :tangle no :results silent
(let ((default-directory (expand-file-name "~/.config/emacs-modular/")))
  (dolist (f (directory-files-recursively "docs/tangles" "^sp-.*[.]org$"))
    (with-temp-buffer
      (insert-file-contents f)
      (when (re-search-forward ":tangle [./]*libraries/modules/" nil t)
        (org-babel-tangle-file f)))))
#+end_src

The same thing from a shell (it works in fish and bash), run from =~/.config/emacs-modular=:

#+begin_src sh :tangle no :eval never
emacs --batch -l org --eval '(dolist (f (directory-files-recursively "docs/tangles" "^sp-.*[.]org$")) (with-temp-buffer (insert-file-contents f) (when (re-search-forward ":tangle [./]*libraries/modules/" nil t) (org-babel-tangle-file f))))'
#+end_src

Afterwards, =git diff= shows what changed. Org ends every tangled file with a newline, so modules that had none gain one, the modules that are still empty are replaced by the skeleton in their literate source, and any literate source edited since its =.el= file brings those edits in.

* Testing a pull request in a sandbox

=emacs-pr= (a fish function in =~/.config/fish/functions/emacs-pr.fish=) starts a second Emacs on the code of a pull request, next to your normal one. Nothing is checked out in =~=, your live configuration keeps running on =main=, and the pull request cannot touch your real notes. It needs yadm, git, fish and Emacs 29 or later (for =--init-directory=), and it assumes macOS with APFS, because it copies files with =cp -c=.

** Usage

#+begin_src sh :tangle no :eval never
emacs-pr 7        # fetch PR #7 and start an Emacs on it
emacs-pr 7        # again, later: update to the PR's latest commit and start again
emacs-pr rm 7     # remove the worktree and the fetched ref of PR #7
emacs-pr reset    # throw away the sandbox notes and home folder
emacs-pr reseed   # throw away the shared package cache
#+end_src

- The PR number is the one on GitHub. The code comes from =pull/N/head= of =origin=, so it works for any PR on the repository, whoever opened it, and needs no branch name.
- The worktree is =~/src/dotfiles-wt/pr-N=, the same folder that =sp-org-issues= and Magit's =% g= use for worktrees. It is a detached checkout of the PR's head, so running =emacs-pr N= again only moves it to the newest commit. Edits you make in it are lost on the next run; commit them on a branch of your own first.
- Close the sandbox Emacs the way you close any Emacs. Run one sandbox at a time (see below).
- When you are done with a PR, =emacs-pr rm N=. The packages stay in the shared cache.

** What it does

1. =yadm fetch origin +pull/N/head:refs/sandbox/pr-N= puts the PR on a ref that is not a branch, so it can never clash with a branch checked out elsewhere. =yadm worktree add --detach= makes the worktree (or =git checkout --detach= updates it).
2. It starts =emacs --init-directory ~/src/dotfiles-wt/pr-N/.config/emacs-modular=. The configuration finds everything relative to =user-emacs-directory=, so the PR's packages, caches and state live in that worktree's =var/=, which git ignores.
3. It sets =HOME= to =~/.cache/emacs-sandbox-home= for that Emacs. Every =~/notes=, =~/bibliography= and =~/Documents= path in the configuration then lands in that folder. The first run fills it with a copy of =~/notes= (an APFS clone, so instant and without extra disk use); later runs reuse it. A PR that writes to the notes only changes the copy.
4. =GIT_CONFIG_GLOBAL= keeps pointing at your real =~/.gitconfig=, so commits in the sandbox still have your name. SSH is unaffected by =HOME=.
5. It remaps the absolute =/Users/.../= entries of =org-agenda-files= (still in =init.el= while the Custom block exists) to the sandbox home.

** Packages are shared, not reinstalled

A fresh worktree has no packages, and elpaca would install all of them again. Instead, the first run clones your live =var/elpaca= into =~/.cache/emacs-sandbox/elpaca= (again an APFS clone). Elpaca's build folders hold /absolute/ symlinks into its =sources/= folder, so the script repoints every symlink that targets the live folder at the copy; without that, a sandbox could rebuild your live packages. Each worktree's =var/elpaca= and =var/cache/eln-cache= are then symlinks into this one cache.

- A PR that uses only packages you already have starts as fast as your normal Emacs, apart from native compilation, which happens in the background and is shared by all sandboxes.
- A PR that adds or updates a package installs just that one into the shared cache. Later PRs see it too.
- Because the cache is shared, run one sandbox at a time: two elpaca processes writing to one folder can corrupt it.
- After you update packages in your live Emacs, run =emacs-pr reseed= to copy the new state next time.

** What is not isolated

- Anything the configuration reaches by an absolute path other than the agenda files (for example =/Users/siainbuletin/...= in a PR's own code) still points at the real folder.
- The sandbox shares your network, your =PATH= and your running programs. A PR that starts a server, syncs with GitHub or calls an external tool does so for real.
- Once the =sp-paths= module is merged, the locations can also be overridden one by one with environment variables such as =SP_NOTES_DIR=. =emacs-pr= does not need them, because it replaces =HOME= as a whole.

** If it goes wrong

- =yadm fetch= fails: check =yadm remote -v= (it needs an =origin= that serves =pull/N/head=, as GitHub does).
- =cp: illegal option -- c=: the folder is not on APFS or =cp= is not the macOS one; copy =~/notes= and =var/elpaca= by hand to =~/.cache/emacs-sandbox-home/notes= and =~/.cache/emacs-sandbox/elpaca=.
- A package fails to load in the sandbox: =emacs-pr reseed= and run again.
- Everything looks stale: =emacs-pr reset= gives you a fresh copy of the notes.
