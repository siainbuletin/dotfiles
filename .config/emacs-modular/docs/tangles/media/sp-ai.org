Literate source for =libraries/modules/media/sp-ai.el=.

- Every line of the module lives in the =emacs-lisp= blocks below, in order.
- The =:tangle= path in the =#+PROPERTY= line at the top says where they are written.
- To tangle, see [[file:../../tangling-instructions.org][Tangling instructions]].

This module installs packages for working with large language models and coding agents from inside Emacs. Most of them are only installed; apart from the Anthropic login for =agent-shell= and turning on =vulpea-mcp=, none of them get keybindings, backends or API keys here, so their defaults (or settings made elsewhere) apply.

The packages:

- =gptel=: a general chat client for many LLM providers, with =gptel-agent=.
- =claude-code=: runs the Claude Code CLI inside Emacs.
- =eca=: Editor Code Assistant.
- =agent-shell=: a shell-like interface to coding agents.
- =efrit=: an agent that runs Claude-driven commands inside Emacs.
- =monet=: the Claude Code IDE protocol for Emacs.
- =vulpea-mcp=: exposes the Vulpea note database to LLMs over the Model Context Protocol.

Dependencies:

- =claude-code= waits for =inheritenv= (from =sp-env=), =vterm= and =eat= (from =sp-terminal=).
- =vulpea-mcp= ties this module to the Vulpea setup in =sp-vulpea-base=.

** claude-code

Installs =claude-code= from Steve Molitor's GitHub repository.

- It runs the Claude Code command-line tool in a terminal buffer inside Emacs.
- =:after= makes it load only once =inheritenv=, =vterm= and =eat= have all loaded. It can use either terminal backend, and uses inheritenv to pass the Emacs environment to the process.
- If any of the three never loads (see the note on =inheritenv= in =sp-env=), claude-code is never configured either.

#+begin_src emacs-lisp -i
;;;; claude-code
(use-package claude-code
  :ensure (:type git :host github :repo "stevemolitor/claude-code.el")
  :after (inheritenv vterm eat))
#+end_src

* Working with AI with my knowledge base

Claude connects to two MCP servers that live inside Emacs:

- =vulpea-mcp=: search and read the notes, create a note.
- =org-mcp=: change existing notes and TODO states.

How they are reached:

- Neither has a network port.
- Claude Code starts the stdio wrapper =emacs-mcp-stdio.sh= (in this folder). It passes every JSON-RPC line to a running Emacs through =emacsclient=.
- So what is needed is any Emacs with a server socket: the GUI one, or a headless daemon.
- =sp-ai= is therefore in the startup list of =init.el=, not among the late modules, so the servers are up as soon as the daemon is.

** mcp-server-lib

Both servers are built on =mcp-server-lib=.

- It is declared before them so that Elpaca doesn't queue it as their dependency and warn about it later (see [[file:../../architecture/load-order.org][the load order]]).
- =mcp-server-lib-start= is called in its =:config=.
- Registering the tools (=vulpea-mcp-enable=, =org-mcp-enable=) does not start the server.
- Leaving the start out gives the =No active MCP server, start server with 'mcp-server-lib-start' first= error, which made the first registration fail with =CONNECTION_CLOSED=.

#+begin_src emacs-lisp -i
;;;; Working with AI with my knowledge base
;; Claude reaches the two MCP servers below through the stdio wrapper
;; `emacs-mcp-stdio.sh', which talks to a running Emacs with `emacsclient'. That
;; Emacs can be a headless daemon: see "Running the MCP servers without a GUI" in
;; docs/tangles/media/sp-ai.org.

;; The server library goes first, so that Elpaca does not queue it as a
;; dependency of vulpea-mcp and org-mcp. It only answers `emacsclient' requests;
;; it opens no port.
(use-package mcp-server-lib
  :ensure t
  :config
  (mcp-server-lib-start))
#+end_src

** vulpea-mcp

=vulpea-mcp= is installed straight from its Codeberg git repository and serves the Vulpea database to MCP-capable agents.

- =vulpea-mcp-enable= is called from the =:config= of the form.
- It used to be called at top level while the module loaded. That fails: Elpaca has not built the package at that point (the module is read during or after init, and use-package bodies run once the package is built).
- The rest of the module (=monet= and the =provide=) was then skipped.

#+begin_src emacs-lisp -i
;; Making an LLM recognise my vulpea notes
(use-package vulpea-mcp
  :ensure (:type git :repo "https://codeberg.org/nicolas-graves/vulpea-mcp.git")
  :config
  (vulpea-mcp-enable))
#+end_src

** org-mcp

=org-mcp= is the server for editing.

- It can change existing headings, TODO states, properties and bodies, add and archive headings, and read the agenda.
- It only touches the files in =org-mcp-allowed-files=, which has to be a list of absolute file names.
- =sp-org-mcp-files= builds it from the Org files directly in =area/= and =inbox/= of the notes directory, the same two folders the agenda reads.
- Anything Claude can reach through =org-mcp= can be changed without a prompt from Emacs. Keep this list as short as you want to trust it.
- After adding a file, run =(setq org-mcp-allowed-files (sp-org-mcp-files))= again.

#+begin_src emacs-lisp -i
;; Editing existing notes and TODO states, which vulpea-mcp cannot do. org-mcp
;; only touches the files in `org-mcp-allowed-files'.
(defun sp-org-mcp-files ()
  "Org files that org-mcp may read and change: those in the agenda directories."
  (cl-loop for dir in (list (sp-path sp-notes-dir "area/")
                            (sp-path sp-notes-dir "inbox/"))
           when (file-directory-p dir)
           append (directory-files dir t "\\.org\\'")))

(use-package org-mcp
  :ensure t
  :config
  (setq org-mcp-allowed-files (sp-org-mcp-files))
  (org-mcp-enable))
#+end_src

** Running the MCP servers without a GUI

Nothing here needs a window. Start a daemon of its own for Claude, with the headless switch so the GUI-only modules (=sp-macos=, =sp-splash=) are skipped, and register the wrapper against its socket:

#+begin_src fish :tangle no
# start (once per login; a launchd agent or `brew services` can run the same command)
emacs --daemon=mcp --headless-host

# check it, and find the socket
emacsclient -s mcp -e '(mcp-server-lib-server-registered-p "vulpea")'
set sock (emacsclient -s mcp -e '(expand-file-name server-name server-socket-dir)' | string trim -c '"')

# register (user scope), no --init-function or --stop-function
claude mcp add -s user -t stdio vulpea -- ~/.config/emacs-modular/emacs-mcp-stdio.sh --server-id=vulpea --socket=$sock
claude mcp add -s user -t stdio org-mcp -- ~/.config/emacs-modular/emacs-mcp-stdio.sh --server-id=org-mcp --socket=$sock
#+end_src

What makes this work (from reading =emacs-mcp-stdio.sh=, =mcp-server-lib= and =org-mcp=):

- The daemon runs the whole of =init.el=, so =sp-ai= registers both servers and starts the library.
- =sp-server= starts the Emacs server in a daemon (its =:if= is =(or window-system (daemonp))=), under the name given after =--daemon=.
- The wrapper only needs the socket.
- A daemon named =mcp= keeps Claude's servers apart from the Emacs you work in, so you can restart either without the other.
- To use the GUI Emacs instead, drop =--socket=. The wrapper then uses the default socket, and both servers are served by it while it runs.

Not tested: none of this has been run against a real daemon from here. Two things to look at the first time:

- That the daemon's init finishes without the GUI modules. The headless switch only skips four modules, so fonts and themes still load.
- That =emacsclient -s mcp -e t= answers before the wrapper is registered.

=vulpea-mcp-explainer.md= in the project files has the troubleshooting table for the =CONNECTION_CLOSED= case.
