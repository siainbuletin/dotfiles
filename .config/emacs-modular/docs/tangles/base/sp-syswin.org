Platform tweaks for running Emacs natively on Windows.

- The only code is a guarded block of three =w32-= variables that speed up subprocess communication and file access.
- Everything else is commentary carried over from Lambda-Emacs suggesting WSL as an alternative.

The module is currently commented out in =init.el= ("will be adding the relevant modules later"), so it is not loaded. Because the code is wrapped in a =system-type= check it would be harmless to enable on macOS or Linux.

The commentary at the top of the module says:

#+begin_quote
This is the specialized module for dealing with launching Emacs on Windows. Because of issues
with the way that Windows accesses the native binaries for Emacs, it might be a better idea to
run Emacs within WSL.

Lambda-Emacs is developed on macOS and Linux; Windows works but needs a little more care. Put
git (and ideally ripgrep) on your Windows PATH, expect the first-run compilation to take
noticeably longer, and prefer a recent official Emacs build with native compilation. Restarting
Emacs to resume installation usually clears transient build failures.
https://codeberg.org/Lambda-Emacs/lambda-emacs#headline-10
#+end_quote

* Settings

** Faster pipes and file attributes on Windows

Only on =windows-nt=, =cygwin= or =ms-dos=:

- =w32-pipe-read-delay= is set to 0, so Emacs does not wait before reading subprocess output.
- =w32-get-true-file-attributes= is turned off, to avoid expensive file ownership lookups.
- =w32-pipe-buffer-size= is raised to 128 KB, so subprocess output is read in bigger chunks.

These help tools like LSP servers and ripgrep. The block ends with the =provide= form.

#+begin_src emacs-lisp -i
(when (memq system-type '(windows-nt cygwin ms-dos))
  (setq w32-pipe-read-delay 0                 ; Faster IPC
        w32-get-true-file-attributes nil      ; Decrease file IO workload
        w32-pipe-buffer-size (* 128 1024)))   ; Read more at a time


(provide 'sp-syswin)
;; sp-syswin.el ends here
#+end_src
