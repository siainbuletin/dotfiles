* Components necessary for making the system work

My academic workflow:

- It is deeply entangled with my practice of writing complex notes that I should always be able to fall back on.
- So I need a robust backlinking system, like the one I had in Obsidian, and a really good completion framework.
- For this, see Quick switcher functionality for Emacs.

My Zettelkasten system is highly personal and complex in the way that I have set it up to reflect my own thinking.

These are the main idiosyncrasies that I want to stay true to as much as possible.

- atomic files :: One note represent one singular idea and nothing more.

- bi-directional linking :: This is crucial for making sure that no information is ever lost on the system. Should also include rendering a special backlink buffer which is relative to the buffer we're currently editing.

- flexible naming :: Being able to name my notes as exactly what they represent within my mind system is essential to my writing workflow. Ideas may be more verbose, so they will be

- tagging files as particular object types :: This allowed me to set up a sort of "pseudo-class" system for my files, which would differentiate their functionality in my knowledge management system. Trying to sketch out how this would work is detailed in [[#Creating an object system just from org-mode files]].

- making the content available to a dynamic buffering a querying system :: This will be replicating the functionality from Dataview, and will be used for dynamic view cration. It can also be used, if needed, for generating backlink panes

- note discoverability :: The bi-directional linking would be essential for building a usable graph of nodes. It's unclear what interface I want for these nodes yet. Mostly I want to work with local graphs. A good bi-directional link pane that is visible next to the note I'm editing can also be quite enough for exploration and finding information again.

The bi-directional linking should also be supplemented by the rendering of a special backlink buffer either contained in the original note, or on the side. If it were within the original note, then it would take up less space on the screen, but it might introduce issues with the overall rendering of the content.

Why not a strict =denote= naming scheme:

- =denote= is recommended a lot for atomic notes, but I don't like that it imposes a strict structure for the naming.
- I want to define my own names and keep them close to the titles, so I can reference them easily in other files.
- This follows the Obsidian scheme a lot, but it's the best way I have found to organise my thoughts.

For writing my personal thoughts, since I _don't want to lose anything_, I use a system that's very based in bidirectional linking. This also has to be easily discoverable through different panes, like emulating the backlink pane that's available at the bottom of a note from Obsidian.

* Packages and paradigms that I explicitily _avoid_

Since there are a lot of options but I'm not particularly happy with any one of them, I will put my criteria for things that I want to specifically _avoid_.

- enclosing the information in databases :: This is completely undesirable because it takes away the possibility for portability of the data. I want my connections to somehow be available even if the =org-roam= package gets deprecated.

- creating an overly complicated cache :: This isn't as important as avoiding a database, but I want to make sure that the system runs as smoothly as it can, which means that everything will noticeably start to crawl at my already 30k-sized vault of notes. Of course, it might be hard to find a functioning system that doesn't cache the links somewhere. This would also allow updating the names across all of the files.

Perhaps this can be remedied in Emacs through using the org ids, but I don't like the way that they litter my manuscript. They should get out of the way as much as possible. I would like to replicate the experience of typing =[[= in my manuscript and getting suggestions for what I want to add (and even to be able to add these new

- imposes naming-schemes :: =denote= does this for the purposes of easier identification. Since I have already formed a workflow which is based on my own lack of naming schemes (but that allows everything to be findable either through title search or full-text search), naming is a big aspect of my workflow for writing overall.

** Changing the display of an org link depending on the type of link it is

Currently, you can change the coloring at least based on the type of org link created. For example, you can differentiate between a generic =file:= link that you may use in =org-mode= and a =denote:= link, which specifically supports the structure of denote.

For example, you can make the link type in =org-ref= (for displaying a citation) to actually display differently.

#+begin_src emacs-lisp :tangle "init.el" :eval never
(defun org-ref-make-org-link-cite-key-visible (&rest _)
  "Make the org-ref cite link visible in descriptive links."

  (save-match-data
    (let ((s (match-string 1))
      (beg (match-beginning 0))
      (end (match-end 0))
      (cite-re (format "^\\(%s:\\)"
               (regexp-opt (-sort
                    (lambda (a b)
                      (> (length a) (length b)))
                    org-ref-cite-types))))
      cite-type)

      (when (and s (string-match cite-re s))
    (setq cite-type (match-string 1 s))
    (remove-text-properties beg end
                '(invisible))
    (add-text-properties
     beg end
     `(face (:foreground ,org-ref-cite-color)))))))

(advice-add 'org-activate-bracket-links :after #'org-ref-make-org-link-cite-key-visible)
#+end_src

This solution is written directly by John Kitchin.[fn:2]
