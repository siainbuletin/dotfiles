This module uses =vertico-posframe= to show the minibuffer (the prompt and Vertico's candidates) in a child frame in the centre of the screen, with some padding. It replaces the former =sp-mini-frame= (see "Why a posframe, and why the name changed" below). It does nothing else; see "What was removed, and why" at the end. The module is loaded in the window-management part of =init.el=, after =sp-tabs=.

* Why a posframe, and why the name changed

The module was called =sp-mini-frame= after the =mini-frame= package it was built on, and was moved to =vertico-posframe= (#136) when =M-x= hung Emacs on macOS. This section compares the two and says how sure the reason for the move is.

** What is known about the hang

- The hang (Emacs at 87 GB of memory, then 98% CPU) was reported after #119, which made the frame resize to its content, and was still reported after #122, #128 and #134.
- When the move was decided, the fixes had not been pulled into the running Emacs, so those tests ran older code than the one named in the reports. The tests do not show that =mini-frame= hangs with the setup of #134 (centred, 4 pixels of padding, fixed height 17, =mini-frame-resize= =not-set=).
- So the change of package is a precaution, not a diagnosis. The cause of the hang was never found.

** The two compared, for this setup

| Question | =mini-frame= | =vertico-posframe= |
|----------+--------------+--------------------|
| What it shows in the frame | Any minibuffer prompt, by advising =read-from-minibuffer=, =read-string= and =yes-or-no-p=, and the =*Completions*= buffer in a second frame | Vertico's prompts only (=completing-read=: =M-x=, files, notes). Plain =read-string= and =y-or-n-p= prompts stay at the bottom of the frame |
| Size | Fits its content (=mini-frame-resize= =t=) or keeps a fixed height. With the larger minibuffer text of =sp-minibuffer= the height had to be worked out by hand (17 lines) | Fits Vertico's candidates itself; nothing to compute |
| Code of its own in this config | Frame parameters, height, resize setting | Four settings |
| Dependencies | None | =posframe=, which many other packages use |
| Fallback in a terminal | Plain minibuffer | =vertico-buffer-mode= |
| Maturity here | Used by this config since the module was written | New to this config; widely used with Vertico elsewhere |
| Known problem here | None found: the hang was reported with it but not traced to it | None yet; not run in Emacs by me |

** Is the change necessary?

Not proven. What follows from the table:

- If =mini-frame= works once the fixes of #134 are really loaded, there is no need to keep =vertico-posframe=; its one advantage is that it needs no height.
- If =vertico-posframe= works, there is no need to go back either: the prompts it leaves out (=read-string=, =y-or-n-p=) are few and short.
- The test that decides it: run the state before #136 (git commit =93c5539=, the merge of #134) after a restart. A hang there is a =mini-frame= problem; no hang means the change of package was not needed, and #137 and #138 can be re-aimed at it.

** The name

The name now says what is used: a posframe. The file, the feature and the doc are renamed, and =init.el= loads =sp-posframe= at the position where it loaded =sp-mini-frame=. Nothing else required the old feature. The old name appears in the history of the CHANGELOG and in notes of the mode line modules (#114, #115), which describe what was true then.

* The posframe

Installs =vertico-posframe= (and =posframe= with it) and turns on =vertico-posframe-mode=, which draws Vertico's minibuffer in a child frame instead of at the bottom of the frame.

- =vertico-posframe-poshandler= is =posframe-poshandler-frame-center=: centred horizontally and vertically.
- =vertico-posframe-border-width= is 4: the padding around the text.
- =vertico-posframe-fallback-mode= is =vertico-buffer-mode=, used in a terminal, where child frames do not exist.
- =vertico-posframe-size-function= is =sp-posframe-get-size=: the width is always =sp-posframe-width-fraction= (0.75) of the parent frame, for every command including the file pickers, so it does not follow the length of the prompt or the candidates (#144, brought back in #163). Width, minimum width and maximum width are all set to that number, and nothing else is changed: the height is the package's own and fits Vertico's =vertico-count= (13, set in =sp-completion=).

#+begin_src emacs-lisp -i
(defcustom sp-posframe-width-fraction 0.75
  "Fraction of the parent frame's width that the posframe always occupies."
  :type 'float
  :group 'minibuffer)

(defun sp-posframe-get-size (buffer)
  "Return the size of the posframe for BUFFER: a fixed share of the frame width.
Width and minimum width are both `sp-posframe-width-fraction' of the frame, so
the posframe does not follow the length of the prompt or the candidates. The
height is left to `vertico-posframe-get-size'."
  (let* ((width (round (* sp-posframe-width-fraction (frame-width))))
         (size (copy-sequence (vertico-posframe-get-size buffer))))
    (plist-put size :width width)
    (plist-put size :min-width width)
    (plist-put size :max-width width)
    size))

(use-package vertico-posframe
  :ensure t
  :after vertico

  :custom
  (vertico-posframe-poshandler #'posframe-poshandler-frame-center) ; centered both ways
  (vertico-posframe-size-function #'sp-posframe-get-size) ; fixed width
  (vertico-posframe-border-width 4)  ; padding around the text
  (vertico-posframe-fallback-mode 'vertico-buffer-mode) ; terminals have no child frames

  :config
  (vertico-posframe-mode 1))
#+end_src

** Border as padding

=sp-posframe--match-border= sets the =vertico-posframe-border= face to the background of the posframe (falling back to =default=), so the 4 pixels of border read as padding. It runs once the package is loaded and on =enable-theme-functions=, so it follows theme changes.

#+begin_src emacs-lisp -i
(defun sp-posframe--match-border ()
  "Give the posframe border the background colour of the posframe itself.
The border then reads as padding. It is run again on every theme change."
  (when (facep 'vertico-posframe-border)
    (let ((bg (or (face-background 'vertico-posframe nil t)
                  (face-background 'default nil t))))
      (when (stringp bg)
        (set-face-attribute 'vertico-posframe-border nil :background bg)))))

(with-eval-after-load 'vertico-posframe
  (sp-posframe--match-border))
(add-hook 'enable-theme-functions (lambda (_theme) (sp-posframe--match-border)))
#+end_src

* Text size

There is no text size of its own: the posframe, like the minibuffer, uses the =default= face. Two ways of enlarging it were tried and removed, and Sia still wants it larger, so this is the open item of the rebuild plan (step 2).

- *#161, face remap per prompt.* =sp-minibuffer= remapped =default= to a larger face and set the =text-scale= on =minibuffer-setup-hook=. The minibuffer was mirrored and =M-x= glitched; removing the hook line stopped it.
- *#174, font on the posframe.* =vertico-posframe-font= was set to a =font-spec= of the =default= family at 1.36 times the =default= height, once at load and on =fontaine-set-preset-hook=. Sia reported that it broke how the window is drawn: the scratch buffer and the dashboard were drawn in the same window and overlapped, and =M-x= could not open =vertico-posframe= until =(vertico-posframe-mode -1)= was evaluated; everything was fine after that. The text-scale part is gone for good and so is the font (#179), together with the =sp-minibuffer-face= face and its fontaine keys.

** Is it fontaine?

Probably not, but this was read from the sources of =fontaine=, =posframe= and =vertico-posframe=, not run in Emacs (none in the container).

- =fontaine= only sets faces: it calls =custom-theme-set-faces= for the faces of the preset (=default=, =fixed-pitch=, =variable-pitch=, the mode lines and the faces added to =fontaine-faces=) and knows nothing about child frames or the =font= frame parameter. Any family it can set on =default= is a normal font, and "Aporetic Sans Mono" is one. A face that is only a =:height= multiple (=sp-minibuffer-face=) is read by the code that wants it; nothing in =fontaine= applies it to a frame.
- The more likely cause is in =posframe=. =vertico-posframe= passes =vertico-posframe-font= as the =:font= of =posframe-show=, which sets it as the font of the child frame (it defaults to the font of the =default= face of the parent). But =posframe= works out the frame's pixel size and position in the font of the parent: =(* (default-font-width) width)= and =(* (default-line-height) height)= in =posframe--set-frame-size= and =posframe--set-frame-size-and-position=, and the same two products as =:posframe-width= and =:posframe-height= for the poshandler that centres it. With a font 1.36 times larger in the child, the text needs more room than the frame is given, which fits the clipping and overlap, and the 75% width of =sp-posframe-get-size= becomes about 100% of the frame. The error that stopped =M-x= was not seen, so this is a guess.
- Not ruled out: that a =font-spec= (rather than a font name string) is not accepted for the frame parameter in that Emacs; that the size in points (=:size= 20.4) differs from the size of the =default= face on that screen; or that the child frame was created before the preset was set.

What to try next, one at a time, each in its own pull request (and set =vertico-posframe-mode= to nil to get =M-x= back if it hangs): (1) =vertico-posframe-font= as a plain font name string with the size in the name, to rule out the font-spec; (2) the same string and a smaller width, so that the width in the child's font is 75%; (3) a larger =default= face for everything, through the fontaine preset (=:default-height=), which keeps every size consistent and needs no posframe setting.

* Rebuilding the setup from zero

The plain setup of #156 is step 0. The plan below adds one thing at a time, each in its own pull request, so a bug points at one change. A step is accepted only when it has passed the checks at the end.

1. *Step 0, the baseline (#156).* Centred frame, padding, nothing else. Use it for a few days in Org with the =*Messages*= popup open. If the glitch or the =*Minibuf-1*= window still happens here, the cause is outside the module (suspects: =popper=, which displays buffers in side windows, and other window hooks such as =sp-set-window-margins= on =window-configuration-change-hook=). In that case find it first, with =emacs -Q= and only =vertico=, =vertico-posframe= and =popper= installed (see the sandbox script in the project files), before adding anything.
2. *Text size.* Still open: #174 tried =vertico-posframe-font= and it overlapped windows and stopped =M-x= (see "Text size" and what to try next there). Never reset =face-remapping-alist= of the minibuffer.
3. *Width.* Set =vertico-posframe-width= or =-min-width= to a number instead of replacing =vertico-posframe-size-function=.
4. *Prompt look.* Style the prompt with the =minibuffer-prompt= face itself (=set-face-attribute=, colours and weight, no =:box= and no =:inverse-video=), for every prompt, not only =M-x=. A look for one command only needs a per-command variable, not a hook that adds remaps.
5. *Dotted line.* Make it part of what Vertico draws, not a second overlay at the end of the input. Options, simplest first: a line character in the prompt string; an advice on the function that formats the candidates; a =vertico-multiform= setting for =execute-extended-command=. Do not create an overlay at =point-max=: Vertico's candidate list lives there and the two compete (in #152's output the dotted line was drawn under the candidates, not under the input).
6. *Dimming.* Leave it out unless it is wanted. If it is, do it once for the whole frame (a translucent frame behind the posframe, or one face for the =default= background of the other windows) instead of remapping faces buffer by buffer; the earlier version remapped over a thousand faces in the buffer behind the posframe.

Checks for every step, before it is merged:

- =M-x=, =C-x C-f=, =C-x b= and a note picker, each opened from the Dashboard, from an Org buffer and from =ibuffer=, with the =*Messages*= popup open and closed.
- Typing slowly and fast, deleting back to empty, and a long input.
- After 10 minutes of working in Org, again.
- =(list vertico-buffer-mode vertico-posframe-mode)= is =(nil t)=, and =(get-buffer-window-list (window-buffer (active-minibuffer-window)) nil t)= has only the minibuffer window and the posframe window.

#+begin_src emacs-lisp :tangle no
