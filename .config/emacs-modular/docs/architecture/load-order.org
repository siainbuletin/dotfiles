#+title: Module load order: what loads when, and why
#+startup: overview

The modules listed in =lem--default-modules= (in =init.el=) are loaded top to bottom, and Elpaca installs the packages of each module as the =use-package= forms are read. The order matters for two reasons, and this page records both, so that a new module can be put in the right place.

1. *A package must be declared before the packages that require it.* Elpaca queues the dependencies of every package it sees. If =org-ql= is declared first, Elpaca queues =org-super-agenda= (which =org-ql= requires) as its dependency, and when the explicit =(use-package org-super-agenda ...)= follows, it warns =org-super-agenda previously queued as dependency of: (org-ql)=. The warning is only logged during init (Elpaca checks =after-init-time=), but Elpaca does not queue the explicit declaration again, so its recipe options (such as =:ensure (:wait t)= or a git source) are not applied.
2. *Anything that stops init costs startup time.* A recipe with =:ensure (:wait t)= makes Elpaca finish its queue up to that point before init goes on, so each one is a barrier. Modules that nothing else needs are loaded after startup instead (see [[*Late modules][Late modules]]).

How to read the boxes and arrows:

- Inside a box the modules are independent of each other.
- An arrow means "has to come before". It points from the package that is required to the one that requires it, the opposite of a dependency arrow.

* Why each arrow is there

Each row is an order the graph enforces: the package on the left must be declared (and, for =:wait t=, installed) before the one on the right. The /source/ column says where the requirement was read from.

The =Package-Requires= headers were read from each package's upstream repository on GitHub. They list names, not recipes, so which Elpaca recipe a name resolves to is not shown here.

* What changed in the order

** =org-ql= moves from =sp-org-base= to =sp-org-agenda=
=org-ql= was installed in =sp-org-base=, the first Org module, and =org-super-agenda= in =sp-org-agenda=, a few modules later. =org-ql= requires =org-super-agenda=, so Elpaca queued it as a dependency and then warned when =sp-org-agenda= declared it explicitly. The =org-ql= form now sits right after the =org-super-agenda= form. Nothing between the two modules uses =org-ql= (=sp-trails= requires it, and loads later).

** =sp-lisp= loads before =sp-prog-misc=
=emr= in =sp-prog-misc= requires =paredit=, which =sp-lisp= installs. The two modules swap places. =sp-lisp= does not use anything from =sp-prog-misc=.

** Late modules

The list of modules that load after startup is the variable =sp-late-modules= in =init.el=; =sp-defer-late-modules= (default =t=) switches the deferral on. At the time of writing it holds =sp-academic=, =sp-notes=, =sp-trails=, =sp-semantic=, =sp-graphs= (graphs of notes, including the relationship annotator and its live view), =sp-embr=, =sp-sandbox=, =sp-vcontrol=, =sp-magit-style=, =sp-merge-pick=, =sp-terminal=, =sp-eshell=, =sp-tag-emoji= and =sp-thesis-dump=, in dependency order (=sp-vcontrol= before =sp-magit-style= and =sp-merge-pick=). =sp-ai= is not in it: it starts the MCP servers that Claude connects to, so it loads with the startup modules (see [[file:../tangles/media/sp-ai.org][sp-ai]]). =lem--default-modules= requires everything else and then calls =sp-schedule-late-modules=, which:

1. adds a function to =elpaca-after-init-hook=, so nothing is queued before Elpaca has finished the packages of the early modules;
2. from there, waits for Emacs to be idle for 0.5 seconds, then requires each late module (a failing one is logged and the rest still load);
3. calls =elpaca-process-queues=, because Elpaca only processes orders declared after init on its own when a command is running interactively.

So the packages of a late module are not installed or loaded during startup but by that last step, and the =:config= of its =use-package= forms runs after that, not while the module is read. With =sp-defer-late-modules= set to =nil= the same list is required straight away, in the same order, during init.

They were picked because no other module =require=s them, and because they install heavy packages (=org-ref= with its dependencies, =magit= with =forge= and =code-review=).

*** What does not work until they have loaded
Keys and commands that are defined, or whose package is installed, by a late module only exist from a second or so after startup:

*** Problems found when checking the order
- *=sp-ai= called =(vulpea-mcp-enable)= at top level.* When the module is read the package is not built yet (Elpaca builds it after the module, and for a late module long after init), so the call failed and =monet= and the =provide= were never reached. It now runs in the =:config= of the =vulpea-mcp= form. =sp-ai= was then taken out of the late list, because Claude's MCP servers have to be up with the daemon.
- *The first version of this page said =sp-keys= autoloads the =magit= commands.* It does not (see above); the page and the comment in =init.el= are corrected.
- No module that loads at startup requires a late one, and the late modules only need packages from modules that load earlier (=org-node=, =denote=, =vulpea=, =transient=, =inheritenv=, =consult=), so their order against the rest has no conflict that I found. =claude-code= (in =sp-ai=) says =:after (inheritenv vterm eat)=, and =vterm= and =eat= come from the late =sp-terminal=, so its configuration waits until that has loaded, which is the intended order.
- =sp-trails= needs =org-ql= from =sp-org-agenda=, which loads earlier, so it is safe as a late module.

*** =sp-tag-emoji= is late, and nothing at startup requires it
=sp-tag-emoji= (with the tag families, =sp-org-tag-families=, defined in it) was in the late list but also =require=d by =sp-tab-inbox=, =sp-collection-query-tables-core=, =sp-move-region-to-heading= and =sp-org-link-conversion=, so it loaded at startup and the late entry only logged =[skip] already loaded=. Those four requires are removed: none of them calls anything from it (they only wanted its side effects, the tag emoji in the =vulpea-select= prompts), and the mode line modules use =fboundp=. Until the late modules have loaded, those prompts show no tag emoji. =sp-graphs=, itself late, still requires it.

** Packages declared twice, and ones declared too late

Elpaca keeps one order per package. A second =:ensure t= for the same package is logged as =Duplicate item ID queued=, and a package that is queued as a dependency before its explicit declaration is logged as =previously queued as dependency of=. Both were in the startup log, and are fixed this way:

Two further errors in the same log were order problems inside a module:

- *=sp-academic=* defined =sp-bibliography=, =sp-bib-notes= and =sp-citar-note= after it required =sp-citations= and =sp-litnotes=. It is a late module, and Elpaca runs the =:init= of a package once it is installed, which can be while the rest of the file is still loading (this is the likely cause; I could not run Emacs to confirm it), so =citar-denote= read =sp-bibliography= while it was void. The three =defcustom= forms are now the first thing in the file.
- *=code-review=* is declared after =forge= but loaded without waiting for it, and its database class needs =emacsql-sqlite-connection=. It now has =:after forge= and requires =emacsql-sqlite= first.

** =sp-fetch-academic= loads inside =sp-academic=

=sp-academic= is one late module, but it requires its sub-modules itself, in this order: =sp-bibprocess=, =sp-pdfprocess=, =sp-citations=, =sp-litnotes=, =sp-fetch-academic=. The new one is last because it reads =sp-bibtex-files= and =sp-bibliography-dir= from =sp-bibprocess= and installs =biblio= (which moved there from =sp-academic=, so =biblio= is still queued once). It needs =org-ref= only when its DOI command runs, so it does not have to come after =org-ref=, which =sp-academic= declares further down.

** What stays as it was
The order inside the UI, tooling and Org groups is unchanged, because I found no requirement between their packages that the current order breaks. Duplicate explicit declarations of one package were first left alone as "not an ordering problem"; Elpaca logs them, so they are fixed (see above). The minimal list (=-minimal=) is as before.

* How to place a new module

1. Find what its packages require (the =Package-Requires= header of each).
2. If a required package is installed by another module, put the new module after it. If it is a package you install in the same module, declare it first.
3. If the rest of init needs the package at load time, give it =:ensure (:wait t)= and keep it near the top. If it is only used interactively, add the module to =sp-late-modules= instead.
4. Add it to the graph above and to the module tree in [[file:../main.org][main.org]].

* What has been checked

- =init.el= and the changed modules were read back by Emacs 29.3 (all forms read); the late-module functions were run against stubs, which loaded the modules in order and asked Elpaca to process its queues.
- The dependency edges come from =Package-Requires= headers on GitHub (see above), not from a run of Elpaca: MELPA is not reachable from where this was prepared, so a real startup with the new order, and with =sp-defer-late-modules= on, has not been done.
- Whether Elpaca installs and configures packages declared after init without further help (the reason =sp-load-late-modules= calls =elpaca-process-queues=) follows from reading =elpaca.el=, and is untested. The same goes for the =:config= of =vulpea-mcp= now running after the package is loaded.
