* Introduction - The inner workings of this literate configuration

Since I want to be able to treat my code in as modular a way as possible, I am separating the modules of my configuration to different org mode files, which will be later tangled to their respective Emacs Lisp modules. This also includes the possibility for the future to tangle to different Emacs Lisp documents, as for now, everything is centralised into a single =init.el= file.

This will allow much simpler debugging when another package is starting to go haywire and will allow writing down personal Lisp modules more easily.

The main file only contains the very basic bootstrapping commands for the package manager. Everything else will be managed in separate files.

This file also serves as a design document for how the documents are also laid out. For more detail into each function, there will be a link added to the relevant =org-mode= configuration module.

Thus, ths entire configuration is built in the style of a README, and more relevant points are to be found in different documents.

The rationale for this configuration is also further explained in "[[file:docs/why-this-literate.org][Why this form of literate configuration?]]".
* Functionality of the literate configuration

If you want a literate configuration that works on smaller files, you need to properly set up the main configuration file (in this case =main.org=). This is the file from which we'll be doing all tasks of transforming the org documents into Emacs Lisp documents.

The process goes as follows:

1. Write the configuration in the main file (=main.org=) or the respective submodules
2. Export the =main.org= file (which has all of the =#+INCLUDE:= directives to =temp.org=
3. From =temp.org=, execute all of the code blocks with =org-babel-execute-buffer=
4. After executing the entire buffer, tangle with the normal =org-babel-tangle=

The =temp.org= file also has to be be evaluated with =C-c C-v C-t=. This will export everything to the proper Emacs Lisp files.

The configuration files (e.g. =init.el= and the modules) will be created upon acting on the =org-babel-tangle= function.

These files can either be "manually" copied to the =~/.emacs.d= directory, or through =Chemacs2=, the literate config can be added as an alternative profile

See also =org-babel-execute-subtree= for the process in which =org-babel= actually works.
** Preparing files for the configuration

When including submodules into the main configuration, they have to be declared as such: =#+INCLUDE: path/to/file.org src org=.

This can also be relative, you don't have to give the full path to the system directory. It can be relative to the directory in which you find =config.org=.
** Being careful while editing the literate configuration

If you don't want to overwrite your changes, you need to make all of the changes directly into the =main.org= file. Then use =C-c C-v C-t= (=M-x org-babel-tangle=) if you want to propagate the changes to the files. The "direction" where each file will be sent is thankfully part of the org source block syntax.

* Protocol for replicating the configuration across machines

Since I have to frequently make use of different computers running different flavors of Arch Linux (and hopefully, in the future, running NixOS or even GNU Guix), I need to have a process for getting these exported configuration files on the other computer as well.

There also needs to be a dependable process for getting any changes while changing between machines.

My current process for dealing with dotfiles is through =chezmoi=, which I prefer to GNU Stow because of its declarative nature and the fact that it doesn't create symlinks. I unfortunately *have* encountered issues with GNU Stow, though I may try again soon (as I don't like how the Git repo for my dotfiles looks like).

* Bootstrapping the package manager in =init.el=

See [[file:~/.config/emacs-include/retired/package-management.org][Past package management configurations]] for why we're using =elpaca= and have adopted other frameworks. In short, =elpaca= allows asynchronous downloading for packages and uses a better dependency management system for making sure that packages work well with one another. Also, =elpaca= has a logging system when installing the packages, which makes debugging easier. This is absent in =straight-el=.

The one thing that's missing from =elpaca= is that it doesn't have lockfiles.

The asynchronous updating for =elpaca= allows for easier building of the configuration on a new machine (this is also thanks to =use-package= integration. Most of the actual initiation happens after the =init.el= file has actually been read.

#+begin_src emacs-lisp :tangle "init.el" :eval never
  (let* ((repo  (expand-file-name "elpaca/" elpaca-repos-directory))
         (build (expand-file-name "elpaca/" elpaca-builds-directory))
         (order (cdr elpaca-order))
         (default-directory repo))
    (add-to-list 'load-path (if (file-exists-p build) build repo))
    (unless (file-exists-p repo)
      (make-directory repo t)
      (when (<= emacs-major-version 28) (require 'subr-x))
      (condition-case-unless-debug err
          (if-let* ((buffer (pop-to-buffer-same-window "*elpaca-bootstrap*"))
                    ((zerop (apply #'call-process `("git" nil ,buffer t "clone"
                                                    ,@(when-let* ((depth (plist-get order :depth)))
                                                        (list (format "--depth=%d" depth) "--no-single-branch"))
                                                    ,(plist-get order :repo) ,repo))))
                    ((zerop (call-process "git" nil buffer t "checkout"
                                          (or (plist-get order :ref) "--"))))
                    (emacs (concat invocation-directory invocation-name))
                    ((zerop (call-process emacs nil buffer nil "-Q" "-L" "." "--batch"
                                          "--eval" "(byte-recompile-directory \".\" 0 'force)")))
                    ((require 'elpaca))
                    ((elpaca-generate-autoloads "elpaca" repo)))
              (progn (message "%s" (buffer-string)) (kill-buffer buffer))
            (error "%s" (with-current-buffer buffer (buffer-string))))
        ((error) (warn "%s" err) (delete-directory repo 'recursive))))
    (unless (require 'elpaca-autoloads nil t)
      (require 'elpaca)
      (elpaca-generate-autoloads "elpaca" repo)
      (let ((load-source-file-function nil)) (load "./elpaca-autoloads"))))
  (add-hook 'after-init-hook #'elpaca-process-queues)
  (elpaca `(,@elpaca-order))

* The files that get created

Ideally, not everything will live in the =init.el= file, so that Emacs Lisp modules may also be evaluated separately for the purposes of debugging or perhaps keeping the installation leaner. Or even for using the same declarative starting point for a configuration even when I'm using Emacs on the Nokia N900 through postmarketOS, where resources are a lot more scarce.

The Emacs Lisp files are organised as such:

- =early-init.el= :: Optimisations for starting up Emacs

- =init.el= :: Contains only the foundations for the functioning of our config. Also, it contains Lisp macros. It will load the different configuration modules that we've defined.

- =sia-modules/= directory :: These are the configuration modules. They don't introduce new bits of Emacs Lisp code, instead they just tweak some configuration for packages.

- =sia-lisp/= directory :: This actually loads custom Emacs Lisp code.

- =sia-ews-functions.el= :: temporary file from where I load helped functions inspired by Emacs Writing Studio.

- =literate-config.org= :: is the current file, which describes the entire architecture.
