* Bootstrapping the package manager in =init.el=

See [[file:~/.config/emacs-include/retired/package-management.org][Past package management configurations]] for why we're using =elpaca= and have adopted other frameworks. In short, =elpaca= allows asynchronous downloading for packages and uses a better dependency management system for making sure that packages work well with one another. Also, =elpaca= has a logging system when installing the packages, which makes debugging easier. This is absent in =straight-el=.

The one thing that's missing from =elpaca= is that it doesn't have lockfiles.

The asynchronous updating for =elpaca= allows for easier building of the configuration on a new machine (this is also thanks to =use-package= integration. Most of the actual initiation happens after the =init.el= file has actually been read.

#+begin_src emacs-lisp :tangle "init.el" :eval never
  ;; Installing elpaca
  (defvar elpaca-installer-version 0.11)
  (defvar elpaca-directory (expand-file-name "elpaca/" user-emacs-directory))
  (defvar elpaca-builds-directory (expand-file-name "builds/" elpaca-directory))
  (defvar elpaca-repos-directory (expand-file-name "repos/" elpaca-directory))
  (defvar elpaca-order '(elpaca :repo "https://github.com/progfolio/elpaca.git"
                                :ref nil :depth 1 :inherit ignore
                                :files (:defaults "elpaca-test.el" (:exclude "extensions"))
                                :build (:not elpaca--activate-package)))

Making the repo directory:

#+begin_src emacs-lisp :tangle "init.el" :eval never
  (let* ((repo  (expand-file-name "elpaca/" elpaca-repos-directory))
         (build (expand-file-name "elpaca/" elpaca-builds-directory))
         (order (cdr elpaca-order))
         (default-directory repo))
    (add-to-list 'load-path (if (file-exists-p build) build repo))
    (unless (file-exists-p repo)
      (make-directory repo t)
      (when (<= emacs-major-version 28) (require 'subr-x))
      (condition-case-unless-debug err
          (if-let* ((buffer (pop-to-buffer-same-window "*elpaca-bootstrap*"))
                    ((zerop (apply #'call-process `("git" nil ,buffer t "clone"
                                                    ,@(when-let* ((depth (plist-get order :depth)))
                                                        (list (format "--depth=%d" depth) "--no-single-branch"))
                                                    ,(plist-get order :repo) ,repo))))
                    ((zerop (call-process "git" nil buffer t "checkout"
                                          (or (plist-get order :ref) "--"))))
                    (emacs (concat invocation-directory invocation-name))
                    ((zerop (call-process emacs nil buffer nil "-Q" "-L" "." "--batch"
                                          "--eval" "(byte-recompile-directory \".\" 0 'force)")))
                    ((require 'elpaca))
                    ((elpaca-generate-autoloads "elpaca" repo)))
              (progn (message "%s" (buffer-string)) (kill-buffer buffer))
            (error "%s" (with-current-buffer buffer (buffer-string))))
        ((error) (warn "%s" err) (delete-directory repo 'recursive))))
    (unless (require 'elpaca-autoloads nil t)
      (require 'elpaca)
      (elpaca-generate-autoloads "elpaca" repo)
      (let ((load-source-file-function nil)) (load "./elpaca-autoloads"))))
  (add-hook 'after-init-hook #'elpaca-process-queues)
  (elpaca `(,@elpaca-order))
#+end_src

** TODO The more verbose/ideal method from the Protesilaos config

To load personal modules (which are configurations of existing packages), as well as custom Lisp functions, I have to define two different locations on the =load-path=:

- =sia-modules= directory :: This is a subdirectory of the parent for emacs configuration. If I weren't using =chemacs2= for configuring my setup, then this would be =~/.emacs.d=. Right now, this directory is =~/.config/emacs=.

  File names are pretty simple: =keybindings.el= defines all specific keybindings, the =academic.el= submodule deals with my academic setup, with all the weeds it might bring with it. *(The academic package may actually be split further, or have other submodules call to it, because it's actually too massive as a usecase.)*

  These modules contain ordinary Emacs Lisp code. At the end of the file there's a call to =provide=, which makes sure that the configurations made are made available to the =init.el= file through =require=.

  A _feature_, in Emacs lingo, is a *variable* whose value is the *entirety* of the file that has the =provide= call within it. Features are *symbols* which are named after the file name (dropping the file extension). For example, if we have a module file called =sia-dark-theme.el=, then the feature it _provides_ for Emacs will be called =sia-dark-theme= and it can be called via =require= within the =init.el= file.

- =sia-lisp= directory :: This where something more traditionally understood as "packages" may reside.

Adding them to the path is done through:

#+begin_src emacs-lisp :tangle no :eval never
  (mapc
   (lambda (string)
    (add-to-list 'load-path (locate-user-emacs-file string)))
  '("sia-lisp" "sia-modules"))
#+end_src
