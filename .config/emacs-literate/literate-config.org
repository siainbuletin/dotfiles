* How is a literate configuration actually done?
** Different methodologies for doing an Emacs literate configuration

*** Loading the org configuration from =init.el= through =org-babel-load-file=

This would be done by calling this block in your =init.el=, and then leaving the rest of the configuration to do its thing:

#+begin_example emacs-lisp :tangle no
(require 'org)
(org-babel-load-file
 (expand-file-name
  "/path/to/config.org"))
#+end_example

The problem with this approach is that it introduces performance issues.[fn:1] Since =org-mode= is loaded *before* actually starting Emacs, the startup time will be impacted significantly. Emacs doesn't need most of the bloat the =org-mode= loads, and it would be much smarter to leave that for the after-=init.el= process.

*** Tangling the org configuration with =org-babel-tangle=

The more *optimal* solution, in this case, is to call =org-babel-tangle=, with the org configuration file open (meaning: the _current_ file, =literate-config.org=), which is *evaluated* through =C-c C-v C-t=. This command updates all of the files that are declared as *targets* through the =:tangle= flag. On the next startup --- or through using the =<F5>= [[*Make reloading the config easier][helper function]] that I designed for reloading the =init.el= file on the fly --- Emacs will have the updated configuration that was detailed in the literate config.

** How can =org-babel= support actual Emacs Lisp configuration?

*This explanation here is for =org-babel-load-file= function, which is _not_ ideal for creating the configuration.*

This works through the =org-babel-load-file= function. To enable the tangling for the files, you need to add this snipped to your =init.el=

#+begin_src emacs-lisp :tangle no
;; Load up Org Mode and (now included) Org Babel for elisp embedded in Org Mode files
(setq dotfiles-dir (file-name-directory (or (buffer-file-name) load-file-name)))

;; load up Org and Org-babel
(require 'org)
(require 'ob-tangle)

;; load up all literate org-mode files in this directory
(mapc #'org-babel-load-file (directory-files dotfiles-dir t "\\.org$"))
#+end_src

What this does is that it compiles each =config.org= file into a =config.el[c]= file. (Remember that the =[c]= in this case denotes that the termination of the file is actually =*.elc=, which denotes compiled Emacs Lisp code.

See also the =load-file= function that is supported by default in Emacs Lisp.

* Structure of the Emacs config

- =early-init.el= :: Optimisations for starting up Emacs

- =init.el= :: Contains only the foundations for the functioning of our config. Also, it contains Lisp macros. It will load the different configuration modules that we've defined.

- =sia-modules/= directory :: These are the configuration modules. They don't introduce new bits of Emacs Lisp code, instead they just tweak some configuration for packages.

- =sia-lisp/= directory :: This actually loads custom Emacs Lisp code.

- =literate-config.org= :: is the current file, which describes the entire architecture.

* Managing the literate configuration

The configuration files (e.g. =init.el= and the modules) will be created upon acting on the =org-babel-tangle= function.

When tangling, the process will create these files:
- =~/emacs-literate/init.el=

These files can either be "manually" copied to the =~/.emacs.d= directory, or through =Chemacs2=, the literate config can be added as an alternative profile

See also =org-babel-execute-subtree= for the process in which =org-babel= actually works.

** How package managament works for Emacs

By default, Emacs uses the =package.el= framework, which is imperative. This makes it harder to manage configuration if you're working between machines. And it's always a lot more convenient to have direct access to the "declaration" of installation if it's written in plain text natively.

=(require)= is used for loading Emacs modules. Emacs Lisp source files call on =(require)= at the beginning of the file so they can get all the modules that they need to function properly. This is what makes a modular configuration possible. Also, through =(require)=, it makes "features" of the code available to be used within a configuration.

con*** Installing =elpaca=

=Elpaca= is a way to have the GUI for the native package manager available (with more modern tweaks), while also having good integration with =use-package=. Hopefully it will make managing the configuration a lot easier in the long run.

Because =elpaca= actually looks into the version requirements for the packages, it's easier to manage dependencies

Another reason why Elpaca is superior to =straight-el= is because it has a logging system for installing packages, which makes it easier to debug when something goes wrong.

The only thing is that it doesn't support lockfiles.

But another downside of =straight-el= is that has a complex bootstrapping process.

This snippet is taken directly from the installation page for Elpaca.

Elpaca also is a lot faster when you need to clone your configuration to a new machine, because it supports asynchronous updating. "You have to move a lot of stuff into :config blocks so it gets run after installing/enabling the package for instance, or you get all kinds of errors. I'm still finding little dark corners."

      (elpaca-generate-autoloads "elpaca" repo)
      (let ((load-source-file-function nil)) (load "./elpaca-autoloads"))))

To load personal modules (which are configurations of existing packages), as well as custom Lisp functions, I have to define two different locations on the =load-path=:

- =sia-modules= directory :: This is a subdirectory of the parent for emacs configuration. If I weren't using =chemacs2= for configuring my setup, then this would be =~/.emacs.d=. Right now, this directory is =~/.config/emacs=.

  File names are pretty simple: =keybindings.el= defines all specific keybindings, the =academic.el= submodule deals with my academic setup, with all the weeds it might bring with it. *(The academic package may actually be split further, or have other submodules call to it, because it's actually too massive as a usecase.)*

  These modules contain ordinary Emacs Lisp code. At the end of the file there's a call to =provide=, which makes sure that the configurations made are made available to the =init.el= file through =require=.

  A _feature_, in Emacs lingo, is a *variable* whose value is the *entirety* of the file that has the =provide= call within it. Features are *symbols* which are named after the file name (dropping the file extension). For example, if we have a module file called =sia-dark-theme.el=, then the feature it _provides_ for Emacs will be called =sia-dark-theme= and it can be called via =require= within the =init.el= file.

* File backup settings

We'll be installing a utility package called =vc-backup= which creates a versioned backup backend

#+begin_src emacs-lisp :tangle "init.el"
  (use-package vc-backup)
#+end_src

Before actually saving a file, what Emacs does is that it takes the contents of the old file and creates a "backup" file for it. These will usually have a =~= attached at the end. As long as you have the file open in the current buffer, the backup will stay at the point _before_ you first opened it. Basically, the backups are done *session by session*.[fn:6]

After you kill a buffer, if you visit the file again, it will create a new backup file, since what you're doing is effectively *starting a new session*.

This code snippet will also make sure that the autosaved files are offloaded to a different folder (for peace of mind). It makes use of the =backup-directory-alist= variable, which can set up file name patterns and backup directory names.

#+begin_src emacs-lisp :tangle "init.el"
  (setq backup-directory-alist
      `(("." . ,(expand-file-name "backups" user-emacs-directory)))
        make-backup-files t
        vc-make-backup-files t ; Won't create backup of files that are already under version control
        backup-by-copying t ; Avoid symlinks
        delete-old-versions t
        delete-by-moving-to-trash t ; This makes sure that the files aren't permanently deleted
        kept-new-versions 6
        kept-old-versions 3
        version-control t)
#+end_src

#+begin_src emacs-lisp :tangle "init.el"
  ;; Customize support for 'emacs -q' (Optional)
  ;; You can enable customizations by creating the nano-custom.el file
  ;; with e.g. `touch nano-custom.el` in the folder containing this file.
  (let* ((this-file  (or load-file-name (buffer-file-name)))
         (this-dir  (file-name-directory this-file))
         (custom-path  (concat this-dir "nano-custom.el")))
    (when (and (eq nil user-init-file)
               (eq nil custom-file)
               (file-exists-p custom-path))
      (setq user-init-file this-file)
      (setq custom-file custom-path)
      (load custom-file)))
#+end_src

*** Integrating with =org-agenda=

To display today’s agenda items on the dashboard, add agenda to dashboard-items:

(add-to-list 'dashboard-items '(agenda) t)
To show agenda for the upcoming seven days set the variable dashboard-week-agenda to t.

(setq dashboard-week-agenda t)
By default org-agenda entries are filter by time, only showing those task with DEADLINE, SCHEDULE-TIME or TIMESTAMP . To show all agenda entries (except DONE)

(setq dashboard-filter-agenda-entry 'dashboard-no-filter-agenda)
To have an extra filter, MATCH parameter is exposed as dashboard-match-agenda-entry variable, by default is nil

‘MATCH’ is a tags/property/TODO match. Org iterates only matched headlines. Org iterates over all headlines when MATCH is nil or t.

See Org Manual for more information.

Once the agenda appears in the dashboard, org-agenda-files stay open. With (setq dashboard-agenda-release-buffers t) the org files are close. Note that this could slow down the dashboard buffer refreshment.

**** Customizing how sorting is done
Agenda is now sorted with dashboard-agenda-sort-strategy following the idea of org-agenda-sorting-strategy. Suported strategies are priority-up, priority-down, time-up, time-down, todo-state-up and todo-state-down

**** Change the aspect of agenda entries
To personalize the aspect of each entry, there is dashboard-agenda-prefix-format which initial value is " %i %-12:c %-10s " where %i is the icon category of the item (see org-agenda-category-icon-alist), %-12:c gives the category a 12 chars wide field and append a colon to the category. A similar padding but for a 10 wide field is %-10s that is for the scheduling or deadline information. For more information see org-agenda-prefix-format.

Deadline or Scheduling time will be formatted using dashboard-agenda-time-string-format and the keywords (TODO, DONE) respect org-agenda-todo-keyword-format.

**** Customizing the format of the tags

To customize the tags format there is a variable dashboard-agenda-tags-format. This variable could be any function that receives the tags directly from org-get-tags. By default dashboard-agenda-tags-format is set to identity. To hide the tags set the variable to ignore: (setq dashboard-agenda-tags-format 'ignore) or to nil.
