3. How is a literate configuration actually done?

3.1. Different methodologies for doing an Emacs literate configuration

3.1.1. Loading the org configuration from init.el through org-babel-load-file

This would be done by calling this block in your init.el, and then leaving the rest of the configuration to do its thing: 

(require 'org)
(org-babel-load-file
 (expand-file-name
  "/path/to/config.org"))

The problem with this approach is that it introduces performance issues.1 Since org-mode is loaded before actually starting Emacs, the startup time will be impacted significantly. Emacs doesn’t need most of the bloat the org-mode loads, and it would be much smarter to leave that for the after-init.el process.

3.1.2. Tangling the org configuration with org-babel-tangle

The more optimal solution, in this case, is to call org-babel-tangle, with the org configuration file open (meaning: the current file, literate-config.org), which is evaluated through C-c C-v C-t. This command updates all of the files that are declared as targets through the :tangle flag. On the next startup — or through using the <F5> helper function that I designed for reloading the init.el file on the fly — Emacs will have the updated configuration that was detailed in the literate config.

3.3. How exactly does a literate configuration manage to be created?

You have a few options for the way that you’re going to create your init.el file. You can create it as an entire file (so it takes the entirety of dotemacs.org, for the case of this document), or it can tangle based on each heading in the org document structure. It can even go as granular as each source block that is declared.

3.4. How can org-babel support actual Emacs Lisp configuration?

This explanation here is for org-babel-load-file function, which is not ideal for creating the configuration.

This works through the org-babel-load-file function. To enable the tangling for the files, you need to add this snipped to your init.el 

;; Load up Org Mode and (now included) Org Babel for elisp embedded in Org Mode files
(setq dotfiles-dir (file-name-directory (or (buffer-file-name) load-file-name)))

;; load up Org and Org-babel
(require 'org)
(require 'ob-tangle)

;; load up all literate org-mode files in this directory
(mapc #'org-babel-load-file (directory-files dotfiles-dir t "\\.org$"))

What this does is that it compiles each config.org file into a config.el[c] file. (Remember that the [c] in this case denotes that the termination of the file is actually *.elc, which denotes compiled Emacs Lisp code.

See also the load-file function that is supported by default in Emacs Lisp.

4. Structure of the Emacs config

early-init.el
Optimisations for starting up Emacs
init.el
Contains only the foundations for the functioning of our config. Also, it contains Lisp macros. It will load the different configuration modules that we’ve defined.
emacs-modules/ directory
These are the configuration modules. They don’t introduce new bits of Emacs Lisp code, instead they just tweak some configuration for packages.
custom-lisp-functions/ directory
This actually loads custom Emacs Lisp code.
literate-config.org
is the current file, which describes the entire architecture.

5. Managing the literate configuration

5.1. How the configuration is created

The configuration files (e.g. init.el and the modules) will be created upon acting on the org-babel-tangle function.

When tangling, the process will create these files:

  • ~/emacs-literate/init.el
  • ~/emacs-literate/early-init.el

These files can either be “manually” copied to the ~/.emacs.d directory, or through Chemacs2, the literate config can be added as an alternative profile

See also org-babel-execute-subtree for the process in which org-babel actually works.

5.2. Making edits to the configuration as needed

When wanting to make changes, you have to go into literate-configuration.org specifically, and then use C-c C-v C-t (M-x org-babel-tangle) if you want to propagate the changes to the files. The “direction” where each file will be sent is thankfully part of the org source block syntax.

;; Adjust garbage collection thresholds during startup, and thereafter

(defmacro k-time (&rest body)
  "Measure and return the time it takes evaluating BODY."
  `(let ((time (current-time)))
     ,@body
     (float-time (time-since time))))

7.3. Installing elpaca

Elpaca is a way to have the GUI for the native package manager available (with more modern tweaks), while also having good integration with use-package. Hopefully it will make managing the configuration a lot easier in the long run.

Because elpaca actually looks into the version requirements for the packages, it’s easier to manage dependencies

Another reason why Elpaca is superior to straight-el is because it has a logging system for installing packages, which makes it easier to debug when something goes wrong.

The only thing is that it doesn’t support lockfiles.

But another downside of straight-el is that has a complex bootstrapping process.

This snippet is taken directly from the installation page for Elpaca.

Elpaca also is a lot faster when you need to clone your configuration to a new machine, because it supports asynchronous updating. “You have to move a lot of stuff into :config blocks so it gets run after installing/enabling the package for instance, or you get all kinds of errors. I’m still finding little dark corners.”

async nature: queues, the fact that most of the init happens after your init.el has been read

7.6.2. TODO The more verbose/ideal method from the Protesilaos config

To load personal modules (which are configurations of existing packages), as well as custom Lisp functions, I have to define two different locations on the load-path:

emacs-modules directory

This is a subdirectory of the parent for emacs configuration. If I weren’t using chemacs2 for configuring my setup, then this would be ~/.emacs.d. Right now, this directory is ~/.config/emacs.

File names are pretty simple: keybindings.el defines all specific keybindings, the academic.el submodule deals with my academic setup, with all the weeds it might bring with it. (The academic package may actually be split further, or have other submodules call to it, because it’s actually too massive as a usecase.)

These modules contain ordinary Emacs Lisp code. At the end of the file there’s a call to provide, which makes sure that the configurations made are made available to the init.el file through require.

A feature, in Emacs lingo, is a variable whose value is the entirety of the file that has the provide call within it. Features are symbols which are named after the file name (dropping the file extension). For example, if we have a module file called sia-dark-theme.el, then the feature it provides for Emacs will be called sia-dark-theme and it can be called via require within the init.el file.

custom-lisp-functions directory
This where something more traditionally understood as “packages” may reside.

Adding them to the path is done through: 

(mapc
 (lambda (string)
  (add-to-list 'load-path (locate-user-emacs-file string)))
'("custom-lisp-functions" "emacs-modules"))

17. File backup settings

We’ll be installing a utility package called vc-backup which creates a versioned backup backend 

(use-package vc-backup)

Before actually saving a file, what Emacs does is that it takes the contents of the old file and creates a “backup” file for it. These will usually have a ~ attached at the end. As long as you have the file open in the current buffer, the backup will stay at the point before you first opened it. Basically, the backups are done session by session.6

After you kill a buffer, if you visit the file again, it will create a new backup file, since what you’re doing is effectively starting a new session.

This code snippet will also make sure that the autosaved files are offloaded to a different folder (for peace of mind). It makes use of the backup-directory-alist variable, which can set up file name patterns and backup directory names. 

(setq backup-directory-alist
    `(("." . ,(expand-file-name "backups" user-emacs-directory)))
      make-backup-files t
      vc-make-backup-files t ; Won't create backup of files that are already under version control
      backup-by-copying t ; Avoid symlinks
      delete-old-versions t
      delete-by-moving-to-trash t ; This makes sure that the files aren't permanently deleted
      kept-new-versions 6
      kept-old-versions 3
      version-control t)
